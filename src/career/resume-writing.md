# 编写简历

写简历的核心不是堆砌技术名词，而是把真实经历整理成招聘方能够快速理解、面试官能够继续追问的证据。

::: info 本章产物
完成本章后，你应该拥有：目标岗位定义、事实证据台账、主简历、岗位定制版简历和发布前检查结果。
:::

## 1. 先确定目标岗位

用一句话定义这份简历服务的岗位：

```text
我是一名有 ____ 年经验的 ____ 工程师，擅长 ____，希望解决 ____ 类型的问题。
```

例如，同一段经历在不同方向的展示重点并不相同：

| 目标方向 | 首屏重点 | 代表证据 |
| --- | --- | --- |
| Java 后端 | 微服务、高并发、数据库与稳定性 | Spring Cloud、缓存、消息队列、可观测性 |
| Java / AI Agent | Java 工程能力 + 已落地 Agent | MCP、Tool Calling、状态机、幂等与人工复核 |
| AI 全栈 | AI 应用交付 + 前后端协作 | Python、Agent 编排、服务接口、Vue 页面 |

一个版本只服务一个主要方向。岗位跨度较大时，保留一份“主简历”，再生成不同的岗位版本。

## 2. 建立事实证据台账

润色前先记录未经包装的事实，不要直接在最终简历上反复改写。

| 维度 | 必须确认的内容 | 可用证据 |
| --- | --- | --- |
| 时间 | 公司、项目的开始和结束时间 | 合同、发布记录、Git 历史 |
| 角色 | 实际职位、个人负责范围、协作边界 | 需求记录、任务分工、代码归属 |
| 技术 | 实际使用的框架、版本和部署方式 | `pom.xml`、配置、源码、流水线 |
| 规模 | 用户、QPS、数据量、设备量及统计口径 | 监控、日志、业务报表 |
| 结果 | 优化前后对比、业务影响、稳定性指标 | 压测、监控、验收或运营数据 |

### 给证据标注可信等级

| 等级 | 含义 | 简历写法 |
| --- | --- | --- |
| 生产经验 | 在线上真实运行并承担业务 | 可以明确写“落地、投产、支撑” |
| 项目经验 | 在完整项目中实现，但未必长期生产运行 | 写清项目场景与完成范围 |
| Demo / 技术验证 | 用于验证方案或学习 | 明确写“Demo、技术验证” |
| 了解 | 阅读或简单使用过 | 放在“了解”，不要写“熟练” |

::: warning 真实性边界
不要把参与写成主导，不要把团队结果全部写成个人成果，不要把 Demo 写成生产项目，也不要填写无法解释测量方式的数字。
:::

## 3. 规划信息结构

推荐顺序：

1. 基本信息与求职方向
2. 个人优势
3. 专业技能
4. 工作经历
5. 项目经历
6. 教育经历

各模块承担不同任务：

| 模块 | 回答的问题 | 写作重点 |
| --- | --- | --- |
| 个人优势 | 为什么值得继续看？ | 3～4 条结论，每条有项目支撑 |
| 专业技能 | 能否快速匹配岗位关键词？ | 按能力域分组，区分熟练程度 |
| 工作经历 | 在什么环境中承担过什么职责？ | 业务范围、岗位责任、工作级结果 |
| 项目经历 | 具体如何解决问题？ | 场景、方案、贡献、取舍、结果 |

## 4. 编写可追问的项目亮点

推荐公式：

> 业务场景 + 关键问题 + 技术方案 + 个人贡献 + 可验证结果

### 从弱表达到强表达

弱表达：

> 负责 Redis 缓存优化，提高了接口性能。

可验证表达模板：

```text
针对【业务场景】中的【具体问题】，我负责【个人贡献】，采用【技术方案】解决【关键难点】，最终将【指标】从【优化前】改善到【优化后】，数据来自【监控 / 压测 / 报表】。
```

没有可靠数字时，可以描述：

- 消除了哪类故障或人工操作。
- 支持了哪些新增业务能力。
- 降低了哪些维护或接入复杂度。
- 建立了哪些可复用组件、规范或流程。

### 使用与贡献相匹配的动词

| 实际贡献 | 建议动词 |
| --- | --- |
| 独立负责方案和落地 | 主导、设计并实现、从 0 到 1 交付 |
| 负责核心模块 | 负责、实现、重构、建设 |
| 与多人共同完成 | 参与、协同、配合、共同推进 |
| 提供建议或验证 | 调研、验证、提出、支持 |

## 5. 区分工作经历与项目经历

工作经历写“职责范围和阶段结果”，项目经历写“实现细节和技术取舍”。

同一个指标最多出现两次：

- 工作经历：强调它带来的业务或团队结果。
- 项目经历：解释它是通过什么方案实现的。

如果两处只是复制粘贴，应删除一处或改为不同层级的证据。

## 6. 编写专业技能

按能力域分组，比按工具清单罗列更容易阅读：

```text
Java 后端（核心） → AI 应用 → 数据与中间件 → 工程化与全栈
```

### 控制熟练程度

| 表述 | 面试预期 |
| --- | --- |
| 精通 | 能解释原理、源码、复杂故障与取舍 |
| 熟练 | 有完整项目经验，能独立解决常见问题 |
| 熟悉 | 使用过并理解核心机制 |
| 了解 | 有学习或验证经历，缺少完整生产证据 |

不要为了通过关键词筛选，把每一项都写成“精通”。技能表述会直接决定面试追问深度。

## 7. 根据 JD 定制

先拆解职位描述，再决定简历内容顺序：

| 岗位要求 | 已有证据 | 证据等级 | 简历位置 | 处理方式 |
| --- | --- | --- | --- | --- |
| Spring Cloud | 多个生产项目 | 生产经验 | 优势、技能、项目 | 前置展示 |
| MCP / Agent | 已投产项目 | 生产经验 | 优势、项目 | 强调工程化细节 |
| 某项陌生技术 | 无生产证据 | 了解 | 技能末尾或不写 | 不包装成项目经验 |

定制时只做四类动作：前置、压缩、删除、补充证据。不要为迎合 JD 添加不存在的经历。

## 8. 管理简历版本

建议保存以下层级：

```text
resume/
├── master/                 # 信息最完整的主简历
├── java-backend/           # Java 后端岗位版
├── java-ai-agent/          # Java / AI Agent 岗位版
└── archive/                # 已投递版本，只读留档
```

文件名包含姓名、方向和日期：

```text
姓名-Java后端-20260821
姓名-Java-AI-Agent-20260821
```

每次投递后保留当时版本，避免面试时不知道对方看到的是哪份内容。

## 发布前检查

- [ ] 公司、项目时间没有冲突
- [ ] 职位名称与真实经历一致
- [ ] “主导、负责、参与”的强度符合个人贡献
- [ ] 每个数字都能解释统计口径和数据来源
- [ ] 工作经历与项目经历没有大段重复
- [ ] 生产经验、项目经验、Demo 和了解已经区分
- [ ] 技术名词拼写、大小写、数字单位和日期格式统一
- [ ] 每个亮点都能回答“为什么、怎么做、你做了什么、结果如何”
- [ ] 公开版本已经完成[隐私检查](./resume-style#隐私分级)
