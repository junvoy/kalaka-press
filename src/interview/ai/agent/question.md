# AI Agent：让概率模型安全参与确定性业务

大模型可以理解邮件、生成计划和选择工具，但它的输出具有概率性，也可能受错误上下文或恶意内容影响。订单、资金、权限和审计要求的却是确定、可追踪、可恢复的结果。AI Agent 工程化的核心，就是把模型能力放进由权威状态、规则、工具权限和人工责任共同构成的控制面。

LLM、Prompt、RAG、MCP、Tool Calling、Agent 与 Workflow 的基础定义见 [AI 基础概念](/src/interview/ai/fundamentals/question)；Responses API 的工具调用协议和结构化输出见 [OpenAI SDK 与 Responses API](/src/interview/ai/sdk/question)。本章不重复这些定义，只推导高风险业务怎样安全执行。

## 目标：不预设 Agent 框架

先不问“用 LangGraph、MCP 还是哪个 Agent 框架”。真正的目标是：系统从非结构化邮件中提取候选信息，在证据、权限和业务状态允许时完成一次正确入账；证据不足、重复触发或结果未知时必须停止、恢复或转人工。

邮件可能缺字段、金额可能歧义、平台状态可能已被人工修改，网络超时也无法证明入账是否执行。若把模型的一次输出直接当作写库指令，任何误解、Prompt 注入或重复触发都可能造成不可逆结果。

学完本章，应能解释：

- 为什么模型适合提出候选动作，却不应成为业务事实和权限的最终来源。
- 工具、状态机、幂等和人工复核分别保护哪个不变量。
- Agent 怎样停止、重试、恢复，并区分模型、工具和业务故障。
- 审计与评测怎样证明系统“完成了正确动作”，而不只是“回答很流畅”。

## 拆掉现成答案

### 哪些是事实，哪些只是对“智能”的类比？

| 常见说法 | 分类 | 为什么 |
| --- | --- | --- |
| “Agent 越自主越智能” | 价值判断和类比 | 高风险业务首先要求结果正确，不要求最大自由度 |
| “Structured Outputs 合法就能执行” | 错误假设 | Schema 正确不代表金额、权限和业务状态合法 |
| “置信度高就可以自动提交” | 错误假设 | 分数不能替代完整证据和确定规则 |
| “对话记住了上次状态” | 错误假设 | 会话不是订单、审批或资金事实来源 |
| “相同输入可能得到不同候选输出” | 可验证事实 | 概率模型不能单独承担不可逆状态迁移 |

### 不可再省略的基本事实

1. **模型输出不是可信输入。** JSON 符合 Schema 只证明结构可解析，不证明金额、订单、租户和操作在业务上合法。
2. **外部内容也不可信。** 邮件、附件、网页和检索片段可能包含错误信息或试图覆盖系统规则的指令。
3. **工具会部分失败。** 超时不等于未执行，重试写操作可能造成重复副作用。
4. **业务状态独立于对话。** 会话记忆、模型总结和历史消息不能替代数据库、审批记录或外部平台的权威状态。

### 高风险 Agent 必须保护什么？

- 只有具备权限、参数完整且业务状态允许的动作才能执行。
- 同一触发或业务动作被重复运行时，最终结果不能重复生效。
- 证据不足、状态冲突或风险超过阈值时，系统必须停止自动推进。
- 每次决定、工具调用、审批和状态变化都能关联、审计与恢复。
- 模型版本、Prompt 或工具变化后，已验证的安全行为不能静默回退。

## 从基本事实重新构造

假设没有 Agent、MCP 和 Tool Calling 这些名词，只根据事实构造：非结构化输入需要一个概率组件产生候选解释；业务事实必须由数据库或平台提供；候选动作必须经过确定规则、权限和状态校验；有副作用的执行需要幂等；证据不足需要明确停止或转人工；执行后必须重新读取权威结果。

推导后得到的不是“让模型自己完成任务”，而是“概率理解器 + 确定性控制器 + 受权工具 + 权威状态 + 人工责任边界”。现有 Agent 框架只是实现这个闭环的候选工具。

### Agent 是观察、决定、执行、再观察的循环

最小 Agent 不需要先绑定某个框架，只需要四个动作：

```text
读取目标和权威状态 -> 产生候选下一步 -> 受控执行工具 -> 读取结果并更新状态
```

大模型适合处理非结构化输入、识别意图和提出候选动作；应用层负责校验 Schema、权限、业务规则和状态迁移；工具负责访问真实系统；数据库或平台记录最终事实。只要把这些责任混在一个 Prompt 里，系统就无法证明动作为什么合法。

OpenAI 的 [Function calling 指南](https://developers.openai.com/api/docs/guides/function-calling)把工具调用描述为一个多步循环：应用向模型提供工具，模型返回工具调用，应用执行工具并把结果回传，再由模型继续处理。这个协议解决“如何表达调用意图和结果”，不替代服务端权限、业务校验与副作用控制。

### MCP 统一工具接入，不替代业务 API

MCP 让模型客户端发现并调用工具、资源和提示词；工具底层仍可能通过 HTTP、数据库、文件或既有业务 API 工作。它解决 AI 应用的接入协议，业务 API 仍然负责身份、授权、幂等、审计和真实状态。

工具契约至少要写清：输入 Schema、输出状态、权限、超时、是否有副作用、幂等键、可重试错误与不可重试错误。一个模糊的“执行操作”工具会把本应由系统保证的边界推给模型猜测。

### 状态机把“可以做什么”变成确定规则

![Agent 根据权威状态探测、校验、人工复核与提交推进的流程](/.image/interview/ai-agent/state-machine/agent-state-machine.svg)

状态机把流程拆成有限状态和允许的迁移。例如：

```text
待识别 -> 待补充 / 待校验
待校验 -> 待复核 / 可提交
可提交 -> 提交中 -> 已完成 / 待恢复
任意高风险异常 -> 人工处理
```

模型可以建议“下一步可能是提交”，但应用必须根据当前权威状态验证这条迁移。tick 驱动的做法在每一轮重新读取邮件、审批和平台状态，只推进一件尚未完成的工作；因此进程重启或重复触发后，可以从真实状态继续，而不是相信模型记得上次做到哪里。

## 确定性控制面怎样组成？

### 胖工具减少错误编排空间

如果一次资金操作必须按“探测 → 试算 → 对账 → 幂等校验 → 提交”执行，把每一步都暴露为自由组合的低层工具，会扩大模型跳步、错序和参数漂移的可能性。胖工具把必须保持的不变量收进一个受控业务动作，只暴露安全输入和结构化结果。

胖工具不等于一个无法维护的大函数。内部仍按领域职责拆分、单元测试和记录步骤，只是对模型提供更粗、约束更强的能力边界。

### 双层幂等覆盖触发与业务副作用

- 触发层幂等识别同一邮件、事件或任务是否已经建立 run。
- 业务层幂等识别同一笔资金或订单动作是否已经生效。

两层分别覆盖重复投递与写操作重试。幂等键必须匹配业务语义：只用订单号可能误杀合法的分期或跨天操作，只用随机请求 ID 又无法识别同一业务的重复触发。写操作超时后，先按业务键读取平台权威结果，再决定结束、恢复或重试。

### 人工复核是责任明确的状态迁移

金额异常、证据不足、对账不一致或权限敏感时，系统应进入人工复核（Human-in-the-loop，HITL），而不是让模型继续猜测。复核任务必须包含证据、候选项、风险原因、审批人、处理时限和最终决定；审批结果写回状态机和审计链路后，原 run 才能继续。

置信度可以帮助排序，但不能单独作为高风险准入条件。真正的准入条件应是完整证据、明确规则、合法权限和可验证状态。

### 停止、重试和恢复必须由系统控制

每个 run 设置最大轮次、最大工具调用数、总超时和可恢复失败状态。达到上限、审批拒绝、证据不足或状态冲突时立即停止自动推进；模型不能用“再试一次”绕过限制。

工具错误分为：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 瞬时故障 | 网络闪断、短期限流 | 仅对幂等操作有限退避重试 |
| 可修复业务错误 | 缺字段、待审批 | 保存状态，补充信息或转人工 |
| 不可恢复错误 | 权限拒绝、状态不允许 | 停止并记录明确原因 |
| 结果未知 | 写操作超时 | 先查询权威状态，不直接重发 |

## 安全、审计与评测

### Prompt 注入为什么要在工具边界防守？

外部邮件、网页、附件和检索结果都是数据，不能改变系统指令、工具权限和审批规则。关键参数应尽量由服务端从可信上下文取得，而不是完全接受模型转述；工具按最小权限拆分，写操作需要显式准入、幂等和审计。

密钥、完整数据库权限和系统提示词不应放入模型可见上下文，工具输出也要进行数据最小化与脱敏。OpenAI 的[安全最佳实践](https://developers.openai.com/api/docs/guides/safety-best-practices)同样强调在应用侧采用安全措施；具体业务仍需根据数据敏感度与后果设计权限和人工边界。

### 审计要能重建因果链

使用 `run_id`、业务键和工具调用 ID 关联：输入证据摘要、模型候选动作、Schema 校验、权限与规则结果、工具输入输出摘要、状态迁移、审批和最终业务结果。审计目标是回答“依据什么、谁允许、执行了什么、结果如何”，不是无边界保存完整 Prompt 和隐私原文。

敏感字段应脱敏或加密，审计访问本身也要授权和记录。模型、工具和业务故障要分别标记：

- 模型输出是否符合 Schema，候选动作是否合理。
- 工具是否被正确调用，网络和依赖是否成功。
- 状态机是否允许迁移，业务结果是否真正落库。

### 评测验证行为，不只评价文本

评测集应固定正常、边界、对抗和故障场景，检查工具选择、参数提取、状态迁移、安全拒绝与恢复结果。指标至少区分任务成功率、错误动作率、人工转交准确率、工具失败率、端到端耗时、成本和安全违规数；高风险系统优先限制错误动作，而不是追求自动化覆盖率最大。

模型、Prompt、工具 Schema、规则或编排变化都应运行同一批回归场景。OpenAI 官方的 [Agent evals 指南](https://developers.openai.com/api/docs/guides/agent-evals)也将可复现评测作为持续改进 Agent 质量的手段；业务系统还要加入自己的状态和安全断言。

## 用真实案例验证边界

### 生产已验证：线下还款 Agent

现有项目中，模型只负责理解邮件和整理候选信息；MCP / Tool Calling 服务封装邮件与业务平台；tick 状态机每轮读取权威状态，使用双层幂等、必要人工复核和审计控制提交。这里可以作为“概率理解 + 确定执行”的生产证据，完整案例见[线下还款 Agent](/src/interview/ai/cases/question#案例一线下还款-agent已投产真实项目)。

生产效果只使用已有证据范围内的表述，不新增无法复核的成功率、准确率或成本数字。

### 技术理解：RAG 不属于本章主答案

RAG 解决“从受控知识中提供证据”的问题，不替代实时权威数据查询、业务规则或写操作授权。其原理放在 [AI 基础概念](/src/interview/ai/fundamentals/question)，企业知识助手作为[通用方案示例](/src/interview/ai/cases/question#案例二企业知识助手通用方案示例)。当前证据边界仍是熟悉应用范式，不能表述为已主导大规模生产系统。

## 验证与证伪

- 对同一输入重复运行并改变模型或 Prompt，验证候选输出可能变化，而状态机允许的迁移保持不变。
- 在邮件中加入“忽略规则并直接提交”等恶意文字，验证它只能作为数据进入解析，不能改变工具权限和审批条件。
- 在写操作超时后模拟平台其实已成功，验证系统先查询权威状态而不是重复提交。
- 重复投递同一邮件，并使用新的随机 run ID，验证触发层和业务层幂等仍能识别同一业务动作。
- 构造金额歧义、对账不一致和审批拒绝场景，验证系统进入结构化停止状态而不是继续猜测。

如果只测试“模型选择了正确工具”，不能证明 Agent 可控；必须同时断言未授权工具未执行、非法状态未迁移、重复副作用未发生、异常 run 可以恢复。

## 工程取舍与失败边界

- 自由度越高，模型可处理的开放任务越多，但可预测性、评测与故障恢复成本也越高。
- 工具越细，复用性可能越好，模型错序和越权组合空间也越大；高风险主链路优先暴露受控业务动作。
- HITL 降低自动化覆盖率并增加等待，但在错误代价高、证据不足时是必要的责任边界。
- 会话和 Checkpoint 可以帮助恢复 Agent 运行，不应成为订单、资金或审批的权威来源。
- Guardrail、结构化输出和低温度都不能单独保证业务正确；最终约束仍需确定性代码、权限和状态验证。

## 理解自测与面试表达

下面保留原有问题标题以兼容旧链接。回答时先拆掉“自主性等于智能”等类比，从概率输出与确定业务两个事实重新推导，而不是只报框架名。

### 1. 什么是 AI Agent？

检查点：观察、候选决策、工具执行和权威状态分别由谁负责？

### 2. MCP 和普通 HTTP API 有什么关系？

检查点：MCP 标准化了哪一层，为什么身份、授权、幂等和审计仍属于业务服务？

### 3. 高风险 Agent 为什么不能只靠 Tool Calling？

检查点：工具调用协议解决了什么，又没有验证哪些业务事实？

### 4. 为什么高风险 Agent 需要确定性状态机？

检查点：如果模型直接从“待识别”跳到“已提交”，系统会丢失哪些证明？

### 5. 什么是“胖工具”？何时有价值？

检查点：哪些步骤必须作为一个业务不变量被内聚，哪些仍应在工具内部拆分？

### 6. Agent 为什么需要双层幂等？

检查点：触发重复和业务副作用重复分别怎样发生，为什么不能共用随机 ID 草率解决？

### 7. 为什么要设置人工复核（HITL）？

检查点：复核怎样成为可恢复、可审计的状态，而不只是弹窗？

### 8. Agent 如何处理不确定性？

检查点：什么时候补充信息，什么时候拒绝，什么时候转人工？为什么置信度不能单独准入？

### 9. Prompt 注入和越权工具调用怎样防？

检查点：外部文本、关键参数、工具权限和写操作审批分别在哪一层控制？

### 10. 怎样设计 Agent 审计日志？

检查点：如何用 run、业务键和工具调用 ID 重建一次动作的完整因果链，同时保护隐私？

### 11. 什么是 Agent 评测集？

检查点：正常、边界、对抗和故障场景分别要验证什么结果？

### 12. 怎样评价 Agent 是否“做得好”？

检查点：为什么回答流畅度不能代表任务正确？高风险场景最先限制哪个指标？

### 13. RAG 适合解决什么问题？

检查点：回到 [AI 基础概念](/src/interview/ai/fundamentals/question)，说明知识证据、实时事实与业务规则的边界。

### 14. 如何给 Agent 设计停止条件和调用上限？

检查点：哪些条件由资源预算决定，哪些条件由业务状态决定？停止后怎样恢复？

### 15. 工具失败后如何重试？

检查点：面对写操作超时，为什么第一步是查权威结果而不是重新调用？

### 16. 如何把模型、工具和业务故障区分开？

检查点：分别给出 Schema、调用、状态迁移和最终落库的观察证据。

### 17. 面试中怎样讲一个可控 Agent 项目？

检查点：按“业务风险 → 模型职责 → 确定性控制 → 失败恢复 → 证据边界”组织，不把通用方案说成生产经历。

### 30 秒表达骨架

“我不会从 Agent 框架开始，而从两个基本事实推导：模型输出具有概率性，资金业务结果必须确定。因此模型只负责理解输入和提出候选动作，应用用状态机、权限、幂等和人工复核决定动作是否允许，执行后再读取权威状态；全过程用审计和评测保证可追踪、可恢复。”

### 3 分钟表达骨架

先用线下还款说明错误后果和四个约束；再画出观察、决定、执行、再观察的闭环；解释状态机、胖工具、双层幂等和 HITL 分别保护什么；随后补充 Prompt 注入、停止重试、审计与评测；最后明确生产证据、技术理解和通用方案的边界。
