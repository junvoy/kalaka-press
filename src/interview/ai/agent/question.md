# AI Agent 工程化面试题

本章对应简历中的 MCP/FastMCP、Tool Calling、确定性 tick 状态机、双层幂等、人工复核、审计脱敏和评测回归。重点是让 Agent 在高风险业务中“可控执行”，而不是只会聊天。

LLM、Prompt、RAG、MCP、Tool Calling、Agent 与 Workflow 的基础定义和适用边界见 [AI 基础概念](/src/interview/ai/fundamentals/question)；工具调用协议、结构化输出与 SDK 参数见 [OpenAI SDK 与 Responses API](/src/interview/ai/sdk/question)。本章只讨论高风险业务的控制面。

## 工具调用与流程控制

### 1. 什么是 AI Agent？

**面试一句话：** Agent 是能理解目标、选择或调用工具、读取结果并推进任务的应用程序；大模型负责理解和决策，但业务约束、权限、状态和执行结果必须由确定性系统管理。

在资金类场景，不能让模型直接决定是否写库。模型输出应经过参数校验、规则校验、权限控制与人工审批边界。

### 2. MCP 和普通 HTTP API 有什么关系？

**面试一句话：** MCP 是让模型客户端发现并调用工具、资源和提示词的标准化协议；工具底层仍可通过 HTTP、数据库、文件或已有业务 API 实现。它解决的是 AI 应用的工具集成规范，不替代业务 API 本身。

工具描述要清楚说明输入、输出、权限和失败语义，不能只给模型一个模糊的“执行操作”入口。

### 3. 高风险 Agent 为什么不能只靠 Tool Calling？

**面试一句话：** Tool Calling 只解决“模型提出调用意图”；高风险场景还必须由应用层校验参数、权限、业务状态和审批条件，并把最终写操作交给确定性服务执行。

模型输出不是可信输入。JSON 解析成功也不代表业务合法，仍需验证金额、订单、租户、环境和操作权限。完整 SDK 调用循环见 [SDK 专题](/src/interview/ai/sdk/question#2-function-calling-的完整闭环是什么)。

### 4. 为什么高风险 Agent 需要确定性状态机？

**面试一句话：** 状态机把流程拆成有限状态和明确迁移条件，使每一轮只能推进一个合法步骤；模型可辅助理解输入，但不能绕过状态与规则直接跳到写操作。

![Agent 根据权威状态探测、校验、人工复核与提交推进的流程](/.image/interview/ai-agent/state-machine/agent-state-machine.svg)

简历中的 tick 思路是每轮重新从邮件和平台权威数据探测状态，选择下一件未完成工作，因此重启或重复触发后仍能安全恢复。

### 5. 什么是“胖工具”？何时有价值？

**面试一句话：** 胖工具把一段必须按固定顺序执行的业务步骤内聚为一个受控操作，例如探测、试算、对账、幂等校验和提交；它能减少模型在多个低层工具间错误编排的机会。

胖工具不等于把所有逻辑堆在一个函数。内部仍应按领域职责拆分、可单测，并返回明确的结构化结果。

### 6. Agent 为什么需要双层幂等？

**面试一句话：** 触发层幂等防止同一邮件或事件被重复处理，业务层幂等防止同一笔资金操作重复提交；两层共同覆盖消息重复、超时重试和跨天重新触发。

幂等键要匹配业务语义。仅用订单号可能误杀合法分期或跨天还款；仅用随机请求 ID 又无法识别同一业务的重复触发。

### 7. 为什么要设置人工复核（HITL）？

**面试一句话：** 人工复核把模型不确定、对账不一致、金额异常或权限敏感的操作转给有权限的人确认，避免自动化系统在证据不足时做不可逆动作。

HITL 不是简单弹窗：要带上证据、候选项、审批人、处理时限和最终决定，并让审批动作进入审计链路。

### 8. Agent 如何处理不确定性？

**面试一句话：** 对无法确定的输入，Agent 应停止自动推进并返回“需要补充信息或转人工”的结构化状态，而不是编造答案或猜测金额、期次和平台。

可把置信度作为辅助信号，但高风险动作的准入条件应是明确规则和完整证据，不是单一分数阈值。

### 9. Prompt 注入和越权工具调用怎样防？

**面试一句话：** 把外部邮件、附件、网页等视为不可信数据，不能让其文本覆盖系统指令；工具按最小权限划分，关键参数在服务端从可信上下文获取，并对写操作设置审批与审计。

不要把密钥、完整数据库权限或系统提示词放进模型可见上下文。工具输出也要过滤敏感信息，防止间接泄露。

### 10. 怎样设计 Agent 审计日志？

**面试一句话：** 用 run_id、业务键和关联 ID 串起模型决策摘要、工具输入输出摘要、状态迁移、审批与最终结果；凭证、手机号、令牌等敏感字段脱敏或加密，并限制审计访问权限。

审计日志的目标是复盘“依据什么、调用了什么、谁批准、结果如何”，不是无边界保存全部 Prompt 和原始隐私数据。

### 11. 什么是 Agent 评测集？

**面试一句话：** 评测集把典型正常、边界和失败场景固定为可重复输入与期望结果，用于验证工具选择、规则决策、状态迁移和安全拒绝是否回归；它是发布前的质量门禁之一。

简历中的黄金场景适合覆盖跨天等额、幂等歧义、防错平台和对账不一致等真实高风险边界。

### 12. 怎样评价 Agent 是否“做得好”？

**面试一句话：** 不能只看回答流畅度，还要看任务成功率、错误动作率、人工转交准确率、工具失败率、端到端耗时、成本和安全违规数，并按高风险场景设硬性门槛。

评测要区分模型能力问题、工具可用性问题和业务规则问题，否则优化方向会跑偏。

### 13. RAG 适合解决什么问题？

**面试一句话：** RAG 先从受控知识库检索与问题相关的内容，再把证据提供给模型生成回答，适合知识会更新、需要引用来源的问答；它不能替代实时权威数据查询和业务规则校验。

当前简历是“熟悉 RAG 应用范式”，回答时应说明技术理解与验证边界，不把它描述为已主导的大规模生产系统。

### 14. 如何给 Agent 设计停止条件和调用上限？

**面试一句话：** 每个 run 都要有最大轮次、最大工具调用数、超时时间和可恢复的失败状态；达到任一上限就停止自动推进，输出明确原因或转人工，而不是无限重试。

停止条件应由业务状态驱动，例如“平台已出现成功记录”“证据不足”“审批被拒绝”。模型的“我还想再试一次”不能自行绕过调用上限。

### 15. 工具失败后如何重试？

**面试一句话：** 先区分瞬时故障、可修复业务错误和不可恢复错误；仅对幂等且瞬时的调用做带退避的有限重试，写操作重试前必须查询权威最终状态。

例如网络超时后，不能直接重发入账请求；先按业务键查询平台是否已成功，再决定结束、恢复或转人工。重试次数、错误码和最终判定必须写入审计日志。

### 16. 如何把模型、工具和业务故障区分开？

**面试一句话：** 为每次运行关联 `run_id`、业务键和工具调用 ID，并分别记录模型输出是否符合 schema、工具是否成功、状态机是否允许迁移以及业务结果是否落库，才能定位责任边界。

排查时先看是否拿到了正确的权威数据，再看模型是否选择了允许的动作，最后核对工具执行与状态迁移。不能把所有失败都归因于“模型幻觉”。

### 17. 面试中怎样讲一个可控 Agent 项目？

**回答框架：** 先说人工流程的风险和自动化目标；再说明模型只负责理解非结构化输入，状态机和胖工具负责受控执行；最后给出幂等、人工复核、审计与评测如何兜底，并说明哪些效果有生产数据、哪些仍是技术验证。

不要只报框架名。面试官更关心“错误会造成什么后果、为什么此处不能交给模型、失败后怎样恢复”。
