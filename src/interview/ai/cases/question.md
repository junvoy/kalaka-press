# AI 应用落地案例

本章用同一套表达模板拆解三个场景：业务目标、架构选择、风险控制、指标与评测、面试讲法和可追问点。**只有案例一来自已投产项目；案例二、三是通用方案示例，不应表述为个人生产经历。**

## 案例一：线下还款 Agent（已投产真实项目）

### 业务目标

监听线下还款邮件，辅助完成批量导入或手工还款等入账流程，降低人工重复操作与错账风险。难点不是“让模型写一段回复”，而是邮件内容不完整、平台状态会变化，且入账属于资金类高风险写操作。

### 架构选择

模型用于理解邮件和整理候选信息；MCP / Tool Calling 服务封装邮件、入账平台、钉钉表格和通知能力；tick 驱动的确定性状态机每轮从邮件与平台权威数据探测状态，再推进一件未完成的工作。

```text
邮件触发 → 读取权威状态 → 参数/权限校验 →
幂等闸门 → 人工复核（必要时）→ 受控提交 → 审计与通知
```

### 风险控制

- 邮件级幂等防止同一触发被重复消费；业务级闸门按平台现有记录确认是否已入账。
- 胖工具内聚探测、校验、提交和结果汇总，减少模型在低层接口之间的错误编排。
- 对证据不足、金额异常、对账不一致等情况停止自动推进，进入人工复核；申请人与审批人分离。
- 用 run ID、业务键、工具结果摘要、状态迁移和审批决定构成可审计链路。

### 指标与评测

生产表达应使用已确认的“运营效率提升 5%”，并补充评测维度：重复入账阻断率、人工转交准确率、工具失败率、端到端耗时、异常恢复成功率。没有测量基准的指标不要临时编造。

### 面试讲法

“我把 LLM 限定在邮件理解和工具选择辅助，不让它直接决定入账。真正的提交由状态机、双层幂等和服务端权限校验控制；证据不足或金额异常会带上上下文转人工，整个过程可从审计记录恢复与复盘。”

### 可追问点

为什么订单号不能单独作为幂等键？超时后如何判断是否已提交？人工审批如何恢复同一个 run？如何区分模型错误、工具错误和业务规则拒绝？

## 案例二：企业知识助手（通用方案示例）

### 业务目标

让员工基于制度、产品手册和 SOP 获得可引用的答案，并避免把过期、无权限或无来源的内容回答成确定事实。它适合解决知识更新快、文档分散的问题，不替代订单、库存等实时权威系统。

### 架构选择

离线侧完成文档解析、清洗、分段、元数据标注、向量索引与版本管理；在线侧先按用户、部门、文档状态过滤，再检索、重排、组织带来源的上下文，最后生成答案或拒答。

```python
documents = retrieve(query, filters={"department": user.department, "status": "published"})
evidence = rerank(query, documents)[:k]
answer = generate_with_citations(query, evidence)
```

### 风险控制

- 权限过滤在检索前完成，不能把无权限片段交给模型后再“要求它忽略”。
- 答案必须绑定来源、版本和生效日期；证据不足时返回“未找到可确认依据”，而不是补全猜测。
- 文档更新后增量建索引，并保留版本，以便定位某次回答使用了哪一版材料。

### 指标与评测

用问题集评估检索召回、引用正确性、答案完整性、拒答正确性和权限泄露数；线上再看自助解决率、人工转接率和负反馈样本。不能只看“回答看起来通顺”。

### 面试讲法

“RAG 的关键不是把 PDF 塞进向量库，而是先把权限、版本和来源作为检索条件，再要求回答给出证据。对于实时数据或没有足够证据的问题，我会路由到受控查询或明确拒答。”

### 可追问点

怎么切分表格和长文档？召回不足和召回噪声如何分别定位？为什么权限过滤必须前置？如何做文档删除和版本回滚？

## 案例三：工单智能分流（通用方案示例）

### 业务目标

把自然语言工单归类、补齐关键信息、匹配知识库，并创建或更新工单；高置信度且低风险的工单可自动分配，复杂、敏感或信息不足的工单由人工处理。

### 架构选择

先用 Structured Outputs 提取类别、优先级、实体和缺失字段；再由规则引擎验证 SLA、客户等级和路由范围；最后才调用受控的创建/更新工单工具。知识检索仅用于建议处理方案，不直接覆盖工单事实。

```python
route = classifier.with_structured_output(TicketRoute).invoke(ticket_text)
decision = validate_route(route, customer_context, sla_rules)
if decision.requires_review:
    create_review_task(decision)
else:
    create_ticket(decision.safe_payload, idempotency_key)
```

### 风险控制

- 结构化输出后仍校验枚举值、字段完整性、租户归属与权限；未知类别不自动硬分配。
- 创建与更新工具携带业务幂等键；网络超时后先查询工单状态再决定是否重试。
- 涉及投诉、隐私、退款或高优先级升级时，强制进入人工审核；外部文本中的指令不能改变系统路由规则。

### 指标与评测

离线统计分类准确率、缺失字段识别率、错误自动流转率和人工接管准确率；线上关注首次响应时长、SLA 违约率、重复工单率与单工单成本。上线门槛应优先限制错误自动流转，而不是追求覆盖率最大。

### 面试讲法

“我会把模型输出限制为可验证的路由建议，路由和写工单由规则与工具权限共同决定。低风险、高证据的路径自动化，高风险或低置信度路径转人工；用同一批脱敏工单做回归，保证优化模型不会提高错分流率。”

### 可追问点

怎样定义低风险工单？类别变更后如何兼容历史数据？如何处理同一客户连续重复提交？人工改判如何回流为评测样本？

## 通用复盘模板

面试讲项目时，按“痛点与边界 → 模型只负责什么 → 哪些由确定性服务保证 → 失败如何恢复 → 用什么指标证明效果”组织。先说风险控制，再说框架与模型，能避免回答沦为名词堆砌。
