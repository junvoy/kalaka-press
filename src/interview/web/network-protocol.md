# 网络协议面试题：从输入网址到服务端响应

这一章不从“七层模型要背哪七层”开始，而从一个可观察的事实开始：用户输入一个网址后，程序必须先找到目标地址、建立可用通道、确认对方身份，再交换应用数据。任何一段失败，都可能表现为“接口慢”或“接口报错”。

题目组织参考了[小林 coding 的网络面试题清单](https://www.xiaolincoding.com/interview/network.html)；文中的协议结论以 RFC 为准，避免把某个操作系统的默认参数说成通用规律。

::: tip 先用这套回答框架
遇到网络题，可以按“**它解决什么不确定性 → 它怎样做 → 还有什么边界**”回答。例如 TCP 的价值不是“绝不丢包”，而是用序号、确认和重传，让两端能把不可靠的网络尽量组织成有序字节流；当连接断开、缓冲区满、应用重复提交时，业务仍要继续处理。
:::

## 一、先建立一张“网络地图”

### 1. OSI 七层和 TCP/IP 四层该怎样回答？

**面试一句话：** OSI 七层适合用来定位职责，工程里更常用 TCP/IP 四层：应用层定义业务消息，传输层负责端到端传输，网际层负责寻址与路由，链路层负责局域网内的一跳交付。

| 常用 TCP/IP 分层 | 要解决的问题 | 常见协议或对象 |
| --- | --- | --- |
| 应用层 | “这段数据对业务代表什么？” | HTTP、DNS、WebSocket、JSON |
| 传输层 | “发给目标机器的哪个进程，如何传输？” | TCP、UDP、端口 |
| 网际层 | “下一跳往哪里走？” | IP、路由、ICMP |
| 链路层 | “在这一段局域网怎样交付？” | Ethernet、MAC、ARP/邻居发现 |

大白话：IP 地址像城市地址，端口像具体窗口号；TCP/UDP 决定怎么送件；HTTP 则定义快递单里的业务内容。不要把“HTTP 在 TCP 上”理解成永远如此：HTTP/3 使用 QUIC，而 QUIC 运行在 UDP 之上。

### 2. IP、端口和 Socket 分别是什么？为什么一台机器能同时访问很多网站？

**面试一句话：** IP 标识网络中的主机或接口，端口标识该主机上的传输层端点；TCP 连接通常由源 IP、源端口、目的 IP、目的端口这四元组区分。

浏览器访问两个 HTTPS 网站时，目标通常都是 `443`，但本机为两条连接分配不同的临时源端口，因此内核知道每个响应该交给哪个 Socket。服务端不能只说“监听 8080”：它是监听某个本地地址和端口，连接建立后每个客户端还有独立的四元组。

### 3. 输入 `https://example.com` 后，发生了什么？

**面试一句话：** 浏览器通常先解析域名得到 IP，再建立或复用连接；若是 HTTPS，还要完成 TLS 握手和证书校验，最后才发送 HTTP 请求并处理响应、缓存和页面资源。

![HTTPS 请求从域名解析、传输连接和 TLS 安全通道，到 HTTP 请求响应的主要路径](/.image/interview/web/io-network/https-request-path.svg)

不要把图背成唯一顺序：浏览器可能命中 DNS/HTTP 缓存，复用连接，或并发加载多个资源；请求也可能先到 CDN、负载均衡或网关。排障时要分别测 DNS、连接、TLS、首字节和下载耗时，不能把总耗时都怪给“后端慢”。

### 4. DNS 解析会经过哪些步骤？缓存为什么会让“刚改域名”不立刻生效？

**面试一句话：** DNS 把域名解析成记录；客户端通常先查浏览器、操作系统或本地递归解析器的缓存，未命中时再由递归解析器向权威链路查询，结果按 TTL 缓存。

DNS 记录不只有 A 记录：IPv6 常用 AAAA，别名常用 CNAME，邮件有 MX，服务发现还可能用 SRV。TTL 是“建议可缓存多久”，不是“到点后全球所有缓存必然同时刷新”；多级缓存、负缓存、CDN 和发布流程都会影响切换观察时间。

**追问：DNS 是不是一定走 UDP？** 不是。常规小查询经常使用 UDP `53`，但 TCP、加密 DNS 和更大的响应也很常见；回答时应说“取决于协议与部署”，不要把一个默认场景当硬规则。

## 二、传输层：TCP 和 UDP 真正解决什么问题

### 5. TCP 和 UDP 怎么选？

**面试一句话：** TCP 提供面向连接、有序字节流和可靠传输机制；UDP 提供较少约束的数据报传输。选择要看业务是否需要顺序、是否能容忍少量丢失、延迟目标和应用层是否愿意自己实现可靠性。

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 数据形态 | 连续字节流，无业务边界 | 一次发送对应一个数据报边界 |
| 顺序与丢失 | 协议层按序交付、重传丢失数据 | 不保证到达、顺序或去重 |
| 拥塞与流控 | 内置机制保护接收方和网络 | 应用或上层协议自行承担治理 |
| 常见场景 | HTTP/1.1、HTTP/2、数据库连接、RPC | DNS、音视频、游戏、QUIC 的承载层 |

UDP 不是“更快的 TCP”，TCP 也不是“绝不丢数据”。例如视频通话中，迟到一秒的旧画面往往没价值；订单创建中，漏掉或重复一次请求都可能有业务后果。

### 6. TCP 为什么需要三次握手？

**面试一句话：** 三次握手让双方确认彼此的收发能力并同步初始序列号，同时避免延迟到达的旧连接请求被误当成新连接；两次不足以让服务端确认客户端收到了它的确认。

![TCP 三次握手建立双向连接，随后以两个方向独立关闭的时序](/.image/interview/web/io-network/tcp-connection-lifecycle.svg)

1. 客户端发送 `SYN`，携带自己的初始序列号，请求连接。
2. 服务端返回 `SYN + ACK`：确认客户端的序号，并给出自己的初始序列号。
3. 客户端返回 `ACK`：确认服务端的序号；双方可以进入 `ESTABLISHED`。

大白话：像两个人对讲。甲说“你能听到我吗”，乙说“能，而且你能听到我吗”，甲再说“能”。三句话才确认双向通路都成立。RFC 9293 仍将防止旧的重复连接初始化视为三次握手的重要目的。

**易错点：** 第三次握手丢失时，不等于连接一定永久失败。服务端会重传 `SYN + ACK`；客户端之后发送的带有正确确认号的数据，也能帮助服务端确认这条连接。具体重传次数和超时由系统实现与配置决定，不要脱离环境死背一个数。

### 7. 为什么 TCP 关闭通常叫“四次挥手”？`TIME_WAIT` 是干什么的？

**面试一句话：** TCP 的两个方向可以独立关闭：一方 `FIN` 表示“我不再发送”，对方先 `ACK`，处理完剩余数据后再发送自己的 `FIN`，最后收到确认；主动关闭方会进入 `TIME_WAIT`，等待足够时间以重发最终确认并隔离旧报文。

服务端收到 `FIN` 后处在 `CLOSE_WAIT`，表示内核已收到对端不再发送的事实，但本地应用还没有完成关闭。线上长期大量 `CLOSE_WAIT`，常见方向是检查应用是否遗漏关闭连接，而不是盲目调大系统参数。

`TIME_WAIT` 不是“无用连接”。它至少解决两件事：最后一个 `ACK` 丢失时能回应对端重发的 `FIN`；让旧连接的延迟报文不会干扰相同四元组的新连接。实际持续时间与操作系统实现有关，不能把“固定 60 秒”当成跨平台结论。

### 8. TCP 如何实现可靠、有序传输？

**面试一句话：** 发送方为字节编号，接收方用确认号说明“下一段希望收到什么”；发送方保留未确认数据并在超时或发现丢失后重传，接收方通过序号排序与去重，最终向应用交付有序字节流。

这里的可靠是“尽力通过协议收敛”，不是业务结果的可靠。TCP 已确认，只代表数据到达对端 TCP 栈；HTTP 200 只代表服务端给出成功响应；扣款、发券等最终业务事实还要由权威状态、幂等键、查询和补偿保证。

### 9. 流量控制和拥塞控制有什么区别？

**面试一句话：** 流量控制保护接收方：它通过接收窗口告诉发送方自己还能接多少；拥塞控制保护网络：发送方根据丢包、确认和往返时间等信号调节发送速率，避免把路径塞满。

大白话：流量控制是在问“你家仓库还放得下吗”；拥塞控制是在看“路上是否堵车”。前者主要看接收端能力，后者主要看网络路径。两者都会限制发送量，但动机不同。

### 10. TCP 有粘包、拆包吗？

**面试一句话：** 更准确地说，TCP 只交付连续字节流，不保留应用消息边界；一次 `read` 可能读到半条、刚好一条或多条业务消息，协议必须定义分帧规则。

常见方案是固定长度、分隔符、长度字段或 TLV。长度字段协议必须校验最大帧长、魔数与版本，不能相信客户端宣称一个超大 body 后就立即分配内存。Java NIO 中怎样累计和解析半包，见[网络与 I/O](./io-network)；Netty 对应的解码器实践见[Netty 框架](./netty)。

## 三、HTTP：请求语义比“能访问”更重要

### 11. HTTP 是无状态的吗？连接复用和会话是不是一回事？

**面试一句话：** HTTP 的请求语义是无状态的：单个请求应能独立理解；但底层 TCP/QUIC 连接可以被复用，业务也可以用 Cookie、Token 或服务端会话保存登录状态，三者不是同一个概念。

连接复用减少建连与握手成本，HTTP/2 还能在一条连接上并发多个流。它不等于“业务有状态”，也不等于“所有请求共享同一个数据库事务”。

### 12. GET、POST、PUT、DELETE 的区别？什么是安全和幂等？

**面试一句话：** HTTP 方法表达意图：GET 读取，POST 通常用于创建或触发处理，PUT 倾向整体替换或按目标 URI 写入，DELETE 删除；“安全”指不应改变服务端业务状态，“幂等”指同一请求重复执行后的预期效果与执行一次相同。

| 概念 | 例子 | 不能误解成 |
| --- | --- | --- |
| 安全（safe） | GET 查询订单 | “绝对没有任何日志或统计副作用” |
| 幂等（idempotent） | 按订单号将状态设为已取消 | “网络层永不重复发送” |
| 非幂等风险 | POST 创建支付单 | “绝对不能重试” |

网络超时只说明调用方没及时得到结果，无法证明服务端没执行。对创建、扣款、发券等 POST，通常用业务幂等键：重试同一键时返回同一业务结果，而不是再创建一份。

### 13. 常见状态码如何回答，才能显得有工程判断？

**面试一句话：** 先按类别理解：`2xx` 成功、`3xx` 重定向、`4xx` 请求侧问题、`5xx` 服务端或网关处理失败；具体状态码要匹配真实语义，并让调用方据此决定是否修正、重试或降级。

| 状态码 | 适合表达的事实 | 常见处理 |
| --- | --- | --- |
| `200` / `201` | 成功读取 / 成功创建资源 | 解析业务响应 |
| `400` | 请求格式或参数不合法 | 调用方修正，不盲目重试 |
| `401` / `403` | 未认证 / 已认证但无权限 | 刷新凭证或申请权限 |
| `404` | 目标资源或路由不存在 | 检查路径、资源标识与发布情况 |
| `409` | 与当前资源状态冲突 | 查询最新状态后处理 |
| `429` | 被限流 | 按 `Retry-After` 或退避策略重试 |
| `502` / `503` / `504` | 网关上游失败 / 暂不可用 / 上游超时 | 结合幂等性做有限退避，并排查网关和下游 |

不要把超时说成 `504`。如果 TCP 连接、DNS 或客户端自身超时，调用方可能根本拿不到任何 HTTP 状态码；`504` 是网关作为 HTTP 响应明确返回的事实。

### 14. HTTP 缓存怎样工作？为什么“接口刚更新却还是旧数据”？

**面试一句话：** 缓存通过 `Cache-Control`、`Expires`、`ETag`、`Last-Modified` 等元数据让客户端或中间缓存复用响应；过期后可用条件请求验证资源是否变化，未变化时服务端返回 `304`，避免重复传 body。

静态资源常用带内容哈希的文件名并设置长缓存；业务数据必须先区分是否允许短暂旧读。缓存问题要沿浏览器、CDN、网关和应用逐层确认响应头与缓存键，不能只在后端改完代码就断言“缓存已经失效”。

### 15. Cookie、Session 和 JWT 怎么选？

**面试一句话：** Cookie 是浏览器随请求携带的一种存储与传输机制；Session 通常是服务端保存状态、客户端只带会话标识；JWT 是可携带声明的令牌格式。选择取决于撤销需求、状态管理、跨端使用与安全策略，不是“JWT 一定无状态更先进”。

无论哪种方案，都要考虑 HTTPS、`HttpOnly`、`Secure`、`SameSite`、过期时间、刷新与退出登录。JWT 一旦发出，服务端若不维护额外状态就难以立即单独撤销；Cookie 自动携带也意味着要按场景防护 CSRF。

## 四、HTTPS、HTTP/2 与 HTTP/3

### 16. HTTPS 比 HTTP 多了什么？TLS 握手究竟解决什么？

**面试一句话：** HTTPS 是在受保护传输通道上的 HTTP；TLS 握手协商协议和算法、验证服务端身份并建立共享密钥，之后用对称加密与完整性保护传输的应用数据。

证书不是“用来加密内容的公钥文件”这么简单。客户端还要验证证书链、域名和有效期，确认自己连的是预期服务。TLS 1.3 的目标包括认证、机密性和完整性；它让后续内容不易被窃听或篡改，但不能替代应用层鉴权、输入校验或防止服务端数据泄露。

**追问：HTTPS 绝对安全吗？** 不是。错误信任证书、终端被入侵、服务端私钥与权限管理失误、钓鱼域名、业务越权都不在“传输已加密”这一句话的保证范围内。

### 17. HTTP/1.1、HTTP/2、HTTP/3 有什么主要差异？

**面试一句话：** HTTP/1.1 通过持久连接减少重复建连但请求并发能力有限；HTTP/2 在一个 TCP 连接上以二进制帧多路复用多个流；HTTP/3 将 HTTP 映射到 QUIC，借助 UDP 承载并把传输层的多路复用和加密能力前移，减少 TCP 层单个丢包阻塞所有流的问题。

| 版本 | 关键改进 | 仍需注意 |
| --- | --- | --- |
| HTTP/1.1 | 持久连接、分块传输 | 管线化兼容性差，通常靠多个连接并发 |
| HTTP/2 | 二进制分帧、多路复用、头部压缩 | 底层仍是单条 TCP 字节流，丢包可能影响连接内其他流 |
| HTTP/3 | HTTP 运行于 QUIC；流独立、支持连接迁移 | UDP 可用性、服务端和网络设备支持、调试与运维成本都要验证 |

不要说“HTTP/3 没有握手、一定更快”。首次访问仍有 DNS、QUIC/TLS 等建立成本；0-RTT 也有重放风险，不能把会产生副作用的请求不加设计地放进去。

## 五、实时通信与网络排障

### 18. WebSocket、SSE 和轮询怎么选？

**面试一句话：** 轮询由客户端定期发请求，简单但有无效流量和延迟；SSE 是服务端到浏览器的单向事件流；WebSocket 建立后支持双向长连接。应按消息方向、频率、连接规模和断线恢复能力选择。

| 方案 | 适合场景 | 关键边界 |
| --- | --- | --- |
| 轮询 | 低频状态刷新 | 间隔越短，成本越高；越长，延迟越大 |
| SSE | 日志流、任务进度、服务端单向通知 | 单向；应处理重连与事件 ID |
| WebSocket | 聊天、协同编辑、双向实时控制 | 要做鉴权、心跳、重连、背压、消息序号与去重 |

长连接不等于可靠业务投递。断线重连期间会丢什么、重复什么、从哪条消息续传，必须由协议和业务状态定义。设备或实时系统中的完整治理可继续看[物联网与实时通信](../iot/question)。

### 19. 一个 HTTP 接口“偶发很慢”，怎样排查？

**面试一句话：** 先把总耗时按 DNS、建连、TLS、请求发送、服务端首字节和响应下载拆开，再用关联 ID 对齐客户端、网关、应用、依赖和基础设施指标，最后根据证据定位而不是先调超时。

可以按下面顺序问：

1. 所有地域和实例都慢，还是只有一部分？先区分全局与局部。
2. DNS、TCP connect、TLS 或 TTFB 哪一段上升？这决定看网络、证书还是应用下游。
3. 网关状态码、应用线程池、连接池、GC、数据库和下游调用的 P95/P99 是否同时异常？
4. 请求是否因超时而重试，造成放大流量？写操作是否有幂等键，避免重复副作用？
5. 修复后是否用相同口径验证成功率、P99、错误率与资源使用？

本地可用 `curl -v` 观察协议与响应头，用 DNS 查询工具确认解析结果；生产环境应使用脱敏的链路追踪、指标和抓包证据，避免在不知情时记录凭证或用户数据。

### 20. 超时、重试和熔断应该怎样一起设计？

**面试一句话：** 超时限制一次等待，重试只用于可安全重试的瞬时故障且要有次数、退避和抖动，熔断在下游持续异常时快速失败并保护资源；三者必须以业务幂等性和端到端时限为前提。

大白话：超时是“不要一直等”；重试是“过一会儿再试一次”；熔断是“发现对方持续故障，先别继续撞门”。如果上游超时 1 秒、下游超时 3 秒，或每一层各自重试三次，就会把一次故障放大成线程、连接和流量雪崩。

对 `TIMEOUT` 或 `UNKNOWN` 的写操作，先按业务键查询权威结果，再决定返回、重试或补偿；不要因为“客户端没收到响应”就直接再扣一次钱或再创建一次订单。

## 六、面试收尾：一段可直接复述的回答

“我会先把一次请求拆成 DNS、传输连接、TLS 和 HTTP 语义四层。TCP 通过序号、确认和重传提供有序字节流，但它不能证明业务是否已经完成；所以对写操作还要设计幂等键和结果查询。线上慢请求也不能只看接口总耗时，我会拆 DNS、connect、TLS、TTFB 和下游耗时，用关联 ID 对齐网关、应用和依赖证据后再调整超时或容量。”
