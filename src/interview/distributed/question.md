# 分布式系统面试题

当服务从一台机器扩展到多台机器后，网络故障、重复请求、时钟差异和部分失败都会出现。本章不追求背概念，而是围绕“怎样让业务结果正确且可恢复”回答。

## 一致性、幂等与事务

### 1. 什么是分布式系统中的 CAP？

**面试一句话：** CAP 讨论发生网络分区时，一致性（C）与可用性（A）无法同时完全保证，分区容错（P）在跨网络系统中通常必须面对；它不是平时只能三选二的简单口号。

真实系统还要讨论延迟、数据模型和业务容忍度。支付余额等关键路径可能更偏向一致性；商品浏览等场景可接受短暂最终一致。

### 2. 什么是 BASE 和最终一致性？

**面试一句话：** BASE 强调基本可用、软状态和最终一致，允许副本或异步流程在短时间内不一致，之后通过消息、重试、对账和补偿收敛到正确状态。

最终一致不等于“不用管”。必须明确哪个状态是权威来源、何时应收敛、失败怎样告警、长期未收敛怎样人工处理。

### 3. 什么是幂等？接口怎样实现幂等？

**面试一句话：** 幂等表示同一个业务请求重复执行，最终结果与执行一次相同；常通过业务唯一键、数据库唯一约束、幂等记录或状态机实现。

![带幂等键的请求处理和重复请求返回流程](/.image/interview/distributed/idempotency/idempotent-request.svg)

Redis 可以辅助抢占和短期去重，但关键写入仍应由数据库唯一约束或可靠状态判断兜底，防止缓存故障或过期后重复执行。

### 4. 什么是分布式事务？为什么不建议轻易使用 2PC？

**面试一句话：** 分布式事务涉及多个独立资源或服务的状态一致；2PC 通过协调者让参与者先准备再提交，能提供强一致语义，但会带来阻塞、可用性和运维复杂度，因此互联网业务常优先拆分为最终一致流程。

不要把“用了 Seata/2PC”当作答案结束。还要说明参与资源、故障恢复、超时、锁持有时间和吞吐影响。

### 5. 什么是 Saga、TCC 和 Outbox？

| 方案 | 核心思想 | 主要代价 |
| --- | --- | --- |
| Saga | 每一步本地事务完成后推进，失败执行补偿 | 补偿逻辑复杂，存在中间状态 |
| TCC | Try 预留、Confirm 确认、Cancel 取消 | 接口侵入强，要处理空回滚和悬挂 |
| Outbox | 本地事务写业务数据与事件，再可靠投递 | 异步延迟，需要投递与幂等机制 |

**面试一句话：** 选择方案前先定义业务能否接受中间状态和补偿，再决定强一致事务还是最终一致编排。

### 6. 什么是分布式锁？什么时候不该用？

**面试一句话：** 分布式锁用于多个节点竞争同一份稀缺资源或临界操作，但它不是数据库唯一约束和幂等设计的替代品；锁要有租约、唯一持有者标识、超时和故障处理。

能用唯一索引、乐观锁或单线程按键串行化解决的问题，通常比全局分布式锁简单可靠。锁服务故障、GC 暂停和主从切换都可能影响锁的正确性。

### 7. 乐观锁和悲观锁怎么选？

**面试一句话：** 乐观锁假设冲突较少，更新时通过版本号或条件更新检测冲突后重试；悲观锁先锁定数据再操作，适合冲突高但会降低并发并增加死锁风险。

扣减库存可使用 `UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0` 这样的条件更新，将校验与扣减放在同一原子操作内。

## 服务治理与可用性

### 8. 什么是服务注册与发现？

**面试一句话：** 服务实例启动后把自身地址和健康状态注册到注册中心，调用方从中获取可用实例并进行负载均衡；注册中心还要通过心跳、超时和摘除处理实例变化。

调用方拿到的地址可能过期，网络也可能抖动，所以客户端仍需超时、重试和熔断。注册中心不是“有了就不会调用失败”。

### 9. 配置中心解决什么问题？

**面试一句话：** 配置中心集中管理不同环境和服务实例的配置，并支持审计、灰度和必要的动态刷新；敏感配置应加密、最小权限访问，不能当作普通文本随意暴露。

动态刷新要区分“新请求读取新值”和“正在执行的任务是否受影响”。涉及连接池、线程池等资源的配置变更，应验证是否支持安全热更新。

### 10. 负载均衡有哪些常见策略？

**面试一句话：** 常见策略有轮询、随机、加权轮询、一致性哈希和最少连接；选择取决于实例能力是否相同、请求耗时是否均衡，以及是否需要同一业务键尽量落到同一节点。

一致性哈希主要用于减少节点变化时的重映射，不保证业务数据一致。负载均衡之外还要有健康检查和异常实例摘除。

### 11. 什么是限流？常见算法有哪些？

**面试一句话：** 限流是在系统接近容量时控制单位时间内允许的请求量，保护服务和下游；常见算法有固定窗口、滑动窗口、漏桶和令牌桶。

令牌桶允许一定突发流量，漏桶更平滑输出。限流应按接口、租户、用户或业务键分层，并返回明确的过载提示与重试建议。

### 12. 什么是熔断、降级和隔离？

**面试一句话：** 熔断在错误率或慢调用超过阈值时暂时快速失败，避免继续压垮故障依赖；降级返回可接受的简化结果；隔离通过独立线程池、连接池或资源配额防止一个依赖拖垮全局。

它们的目标是“故障不扩散”。阈值应由真实容量和错误预算决定，并配套恢复探测、监控和演练。

### 13. 重试为什么可能造成雪崩？

**面试一句话：** 当下游已经变慢或故障时，大量调用方立即重试会放大请求量，进一步压垮下游；因此重试只用于可能恢复的错误，并设置次数上限、指数退避、抖动和总超时预算。

写操作的重试必须先保证幂等。超时不代表服务端一定没有执行成功，盲目重试很容易产生重复扣款、重复下单等问题。

### 14. 分布式 ID 方案有哪些？

**面试一句话：** 常见方案有数据库自增号段、UUID、雪花算法和号段服务；选择时要权衡唯一性、有序性、长度、生成性能、时钟依赖和数据库索引友好性。

随机 UUID 容易导致索引局部性变差；雪花算法依赖机器标识和时钟处理；数据库号段实现直观但需预取和容灾。业务展示编号与数据库物理主键也可以分离。

### 15. 怎样设计一个可观测、可恢复的分布式流程？

**面试一句话：** 给每次请求和每个事件建立关联 ID、业务唯一键和状态机，记录关键状态转换；围绕成功率、延迟、积压、重试和未收敛记录设置监控与告警，并准备可幂等执行的补偿工具。

可观测性不是只打日志：日志、指标和链路追踪各自回答不同问题。涉及资金、订单等关键流程时，还要保留审计记录和人工复核入口。
