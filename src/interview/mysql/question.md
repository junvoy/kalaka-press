# MySQL 面试题

这页按“**面试能说清** + **大白话能讲明** + **源码知道从哪里看**”组织。回答时先给结论，再解释原理，最后补充适用边界；不要只背名词。

## MySQL 的逻辑架构是怎样的？

MySQL 可以分为 **Server 层** 和 **存储引擎层**：

- **Server 层**：负责连接管理、权限校验、SQL 解析、优化和执行，并提供函数、存储过程、触发器等能力。
- **存储引擎层**：负责数据的存储和读取。常用的 InnoDB 支持事务、行级锁、外键和崩溃恢复。

一条查询 SQL 通常会经过：连接器 → 解析器 → 优化器 → 执行器 → 存储引擎。

**大白话：** MySQL 的 Server 层像餐厅前台和调度员：确认你是谁、看懂你点什么、挑一条更省事的路线；InnoDB 像后厨和仓库，真正把数据拿出来或改掉。

![MySQL 一条 SQL 从连接、解析、优化到 InnoDB 执行并返回结果的流程](/.image/interview/persistence/mysql/mysql-query-execution.svg)

**源码切入：** 阅读 MySQL Server 源码时，可从 [`sql/sql_parse.cc`](https://github.com/mysql/mysql-server/blob/trunk/sql/sql_parse.cc) 的 SQL 解析入口、[`sql/sql_optimizer.cc`](https://github.com/mysql/mysql-server/blob/trunk/sql/sql_optimizer.cc) 的优化器，再到 [`storage/innobase/`](https://github.com/mysql/mysql-server/tree/trunk/storage/innobase) 的 InnoDB 实现顺序跟踪。面试中不用报函数名，但要能说出“Server 决定怎么查，引擎负责怎么取数据”。

## InnoDB 和 MyISAM 有什么区别？

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行级锁为主，也支持表级锁 | 表级锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持 | 能力较弱 |
| 索引组织 | 聚簇索引 | 非聚簇索引 |
| 适用场景 | 高并发读写、需要事务 | 以读为主且不需要事务的旧系统 |

MySQL 5.5 之后，InnoDB 是默认存储引擎，业务系统通常优先选择 InnoDB。

**大白话：** MyISAM 更像一本只能整本占住修改的账本；InnoDB 能把账、锁和故障恢复配套做好，所以订单、库存、支付等业务通常选它。

## 为什么 InnoDB 推荐使用自增主键？

InnoDB 使用主键组织聚簇索引，叶子节点按主键顺序存放完整行数据。自增主键具有以下优点：

1. 新数据通常追加到索引末尾，减少页分裂和数据移动。
2. 整数比较速度快，索引占用空间小。
3. 二级索引的叶子节点会保存主键值，主键越短，二级索引越节省空间。

随机 UUID 会让插入位置分散，更容易产生页分裂和索引碎片。如果业务必须使用 UUID，可以考虑将有序 ID 作为物理主键，并对业务 UUID 建唯一索引。

**大白话：** 自增主键像按号码入座，新记录通常接在最后；随机 UUID 像让每位新同学随机插进全班座位，书页更容易被拆开重排。业务 UUID 仍可保留，但更适合做唯一业务编号而非物理主键。

## MySQL 索引为什么使用 B+ 树？

B+ 树适合磁盘和范围查询：

1. 非叶子节点只保存键和子节点指针，单页可以容纳更多键，树的高度更低，磁盘 I/O 更少。
2. 所有数据都在叶子节点，查询性能更稳定。
3. 叶子节点通过链表相连，范围查询和排序可以顺序扫描。
4. 相比哈希索引，B+ 树既支持等值查询，也支持范围、排序和最左前缀匹配。

**大白话：** B+ 树像按目录排好的书架：先用少量目录页找到范围，再顺着相邻书页往后翻。哈希索引像“名字 → 某一页”的速查表，查一个精确名字很快，但不擅长找“100 到 200”。

## 聚簇索引和二级索引有什么区别？

- **聚簇索引**：叶子节点保存完整行数据。InnoDB 通常使用主键作为聚簇索引，一张表只能有一个。
- **二级索引**：叶子节点保存索引列和对应的主键值。一张表可以有多个二级索引。

通过二级索引查询非索引列时，需要先得到主键，再到聚簇索引查询完整数据，这个过程叫作 **回表**。

![MySQL 二级索引查询在覆盖索引和回表之间分支的流程](/.image/interview/persistence/mysql/mysql-secondary-index-lookup.svg)

**源码切入：** InnoDB 的行读取逻辑集中在 [`storage/innobase/row/row0sel.cc`](https://github.com/mysql/mysql-server/blob/trunk/storage/innobase/row/row0sel.cc)。先从二级索引找到主键、再去聚簇索引取行，是理解“回表”时最重要的数据路径；只需要索引列时，优化器可以避免第二次查找。

## 什么是覆盖索引？

查询需要的列全部包含在某个索引中，无须回表，这个索引就称为覆盖索引。

例如存在联合索引 `idx_user_status(user_id, status)`：

```sql
SELECT user_id, status
FROM orders
WHERE user_id = 1001;
```

该查询可以直接从联合索引返回结果。覆盖索引能够减少随机 I/O，但不应为了覆盖所有查询而创建过宽的索引，否则会增加存储空间和写入成本。

**大白话：** 覆盖索引就是“索引卡片上已经写全了你要的信息”，不用再去翻完整档案；但卡片不能无限加内容，否则每次写数据都要维护一大摞卡片。

## 什么是最左前缀原则？

联合索引会按照索引列从左到右排序。假设索引为 `(a, b, c)`，通常可以支持：

- `a`
- `a, b`
- `a, b, c`
- `a` 等值匹配后对 `b` 或 `c` 做范围、排序等操作

如果跳过最左侧的 `a`，通常不能利用该联合索引完成高效定位。设计联合索引时，一般把区分度较高、经常作为等值条件的列放在前面，同时结合实际查询、排序和分组需求判断。

**大白话：** `(a, b, c)` 像按“省、市、区”排好的电话簿。知道省才能快速缩小到市和区；只给一个区名，通常不能直接从这本簿子定位。

## 哪些情况可能导致索引失效或无法充分使用？

常见情况包括：

1. 联合索引不满足最左前缀原则。
2. 对索引列进行函数计算或表达式运算，如 `DATE(create_time) = '2026-08-21'`。
3. 隐式类型转换，例如字符串列使用数字条件比较。
4. 使用以通配符开头的模糊查询，如 `LIKE '%keyword'`。
5. 对索引列使用不利于范围定位的条件，如部分 `OR`、`NOT IN`、`!=` 查询。
6. 优化器判断全表扫描成本更低，例如返回数据占表中比例过高。

是否真正使用索引，应以 `EXPLAIN` 和实际执行统计为准，不能只凭 SQL 形式判断。

## 如何分析 EXPLAIN 的结果？

重点关注以下字段：

- `type`：访问方式。常见性能趋势为 `const` > `ref` > `range` > `index` > `ALL`。
- `possible_keys`：优化器可能选择的索引。
- `key`：实际使用的索引。
- `key_len`：使用的索引长度，可辅助判断联合索引使用了哪些列。
- `rows`：预计需要扫描的行数。
- `filtered`：经过条件过滤后预计保留的百分比。
- `Extra`：补充信息，如 `Using index`、`Using temporary`、`Using filesort`。

`Using filesort` 不一定表示使用磁盘排序，`Using temporary` 也不一定必然很慢。分析时要结合扫描行数、数据量、SQL 延迟以及 `EXPLAIN ANALYZE` 的实际执行信息。

**大白话：** `EXPLAIN` 是出发前的导航计划，`EXPLAIN ANALYZE` 是实际跑完后的行车记录。前者告诉你“准备怎么走”，后者更能证明“实际上走了多少路、花了多久”。

## 一条慢 SQL 应该如何排查和优化？

可以按以下顺序处理：

1. 通过慢查询日志、监控或链路追踪定位 SQL、耗时和调用频率。
2. 使用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 查看访问方式、扫描行数、索引和排序情况。
3. 检查索引是否缺失、冗余，联合索引顺序是否匹配查询条件。
4. 减少返回列和扫描行数，避免 `SELECT *`，尽量使用覆盖索引。
5. 优化深分页、复杂子查询、不必要的排序和大事务。
6. 确认是否存在锁等待、连接池耗尽、磁盘 I/O 或 Buffer Pool 命中率低等问题。
7. 在接近生产的数据量和分布下验证优化效果，并关注写入成本和其他 SQL 的回归。

**面试作答顺序：** “我先确认慢在什么 SQL、调用多不多；再用 `EXPLAIN ANALYZE` 看实际扫描和执行；随后按查询条件调整索引或 SQL；最后在接近生产的数据分布下验证延迟、写入成本和回归。”这样能避免一上来就说“加索引”。

## 深分页为什么慢？如何优化？

```sql
SELECT *
FROM orders
ORDER BY id
LIMIT 1000000, 20;
```

MySQL 需要先定位并跳过前 1000000 行，再返回 20 行；如果查询包含非索引列，还可能发生大量回表。

常用优化方式是基于上一页最后一个排序键做游标分页：

```sql
SELECT *
FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

如果必须跳转到指定页，可以先通过覆盖索引查询主键，再与原表关联。排序键应稳定且唯一，例如使用 `(create_time, id)` 避免同一时间值导致数据重复或遗漏。

**大白话：** `LIMIT 1000000, 20` 相当于每次都从第一页翻掉一百万条再拿 20 条；游标分页是记住上次翻到哪一条，然后从那里继续翻。

## 什么是事务的 ACID？

ACID 描述的是一个可靠事务应具备的四个性质。可以用“创建订单 + 扣减库存”这笔事务理解：

| 特性 | 专业含义 | 大白话 | InnoDB 主要机制 |
| --- | --- | --- | --- |
| 原子性（Atomicity） | 事务中的操作作为一个整体，要么全部成功，要么全部失败 | 不能订单创建成功了，库存却没有扣 | undo log、回滚机制 |
| 一致性（Consistency） | 事务前后数据都满足约束和业务规则 | 事务结束后，库存、订单状态、金额仍然对得上 | ACID 共同作用，加上约束和业务代码 |
| 隔离性（Isolation） | 并发事务的中间状态不能随意互相干扰 | 两个人同时抢最后一件商品，不能都扣减成功 | 锁、MVCC、隔离级别 |
| 持久性（Durability） | 已提交的数据在发生故障后仍能恢复 | 页面已经显示下单成功，数据库重启后订单不能消失 | redo log、刷盘和崩溃恢复 |

### 四个性质容易混淆的地方

- **原子性关注“做一半失败怎么办”**。例如第二条 SQL 报错时，前面已经执行的修改要能够回滚。
- **一致性是最终目标，不是某一个日志单独保证的**。数据库可以保证唯一键、外键、非空等约束，但“余额不能为负”“订单金额必须等于明细之和”仍需要正确的业务逻辑。
- **隔离性关注并发执行**。事务单独运行没有问题，不代表多个事务同时运行也不会超卖或覆盖数据。
- **持久性关注提交后的故障恢复**。它不等于每种刷盘配置都保证绝对零丢失，可靠性还与 `innodb_flush_log_at_trx_commit`、操作系统和存储设备有关。

**面试一句话：** ACID 分别解决事务执行一半失败、事务结果违反规则、并发事务互相干扰以及提交后宕机丢数据的问题；InnoDB 主要通过 undo log、锁与 MVCC、redo log 实现底层保障，一致性还需要数据库约束和业务代码共同保证。

## MySQL 有哪些事务隔离级别？

隔离级别规定一个事务能够看到其他并发事务的哪些结果。理解四个级别前，先区分三种问题：

| 并发现象 | 含义 | 例子 |
| --- | --- | --- |
| 脏读 | 读到了其他事务尚未提交的数据 | A 读到 B 修改后的余额，随后 B 回滚 |
| 不可重复读 | 同一事务两次读取同一行，值发生变化 | A 第一次读余额为 100，B 提交修改后，A 再读变成 80 |
| 幻读 | 同一事务两次按相同范围查询，结果行数发生变化 | A 查询“库存大于 0”有 10 行，B 插入后 A 再查有 11 行 |

**大白话：** 脏读是读到“还没定稿的数据”；不可重复读是“同一个人前后变了”；幻读是“符合条件的人数前后变了”。

按照 SQL 标准，四个隔离级别的能力可以这样记：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 直观理解 |
| --- | --- | --- | --- | --- |
| 读未提交（READ UNCOMMITTED） | 可能 | 可能 | 可能 | 别人还没提交也能看，隔离最弱 |
| 读已提交（READ COMMITTED） | 避免 | 可能 | 可能 | 每条语句只能看已提交数据，但两次查询可能不同 |
| 可重复读（REPEATABLE READ） | 避免 | 避免 | 标准允许 | 同一事务的普通查询通常复用同一份快照 |
| 串行化（SERIALIZABLE） | 避免 | 避免 | 避免 | 尽量让并发事务表现得像排队执行 |

### InnoDB 的 RR 为什么经常说“解决了幻读”？

上表描述的是 SQL 标准。InnoDB 默认使用 RR，并做了更具体的实现：

- **普通 `SELECT` 的快照读**通过 MVCC 复用 Read View，第二次查询通常仍看到同一份快照，因此不会看到其他事务后来提交的新增行。
- **`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 等当前读**会对扫描到的索引记录和范围使用记录锁、间隙锁或 next-key lock，阻止其他事务在相关间隙插入。

所以面试中更准确的说法是：**SQL 标准的 RR 仍允许幻读；InnoDB 通过 MVCC 处理快照读，通过 next-key lock 等机制处理当前读中的幻读问题。** 不要只回答“RR 一定有幻读”或“RR 完全没有幻读”。

### RC 和 RR 在业务中怎样选择？

| 对比项 | RC | RR |
| --- | --- | --- |
| 普通查询快照 | 每次一致性读创建新快照 | 通常复用第一次一致性读的快照 |
| 数据新鲜度 | 更容易看到刚提交的数据 | 同一事务内结果更稳定 |
| 范围锁 | 通常不使用 gap lock，外键和重复键检查等除外 | 当前读可能使用 gap lock / next-key lock |
| 适合场景 | 希望减少范围锁、接受同一事务两次查询不同 | 需要同一事务内重复查询结果稳定 |

隔离级别越强，通常意味着更严格的可见性或更多锁等待，但不能只凭级别判断性能。还要结合事务长度、索引、SQL 访问范围和并发冲突测试。

```sql
-- 查看当前会话隔离级别
SELECT @@transaction_isolation;

-- 设置当前会话后续事务使用 RC
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

另外，隔离级别不能自动解决所有并发业务问题。例如两个请求都先查询库存为 1，再各自执行扣减，仍需要条件更新、悲观锁、乐观锁或唯一约束等手段防止超卖和丢失更新。

**面试一句话：** 四个隔离级别是在一致性和并发能力之间做取舍。InnoDB 默认 RR，普通查询用 MVCC 保持可重复读，当前读用 next-key lock 等机制保护索引范围；RC 每次查询读取新快照、范围锁更少，但同一事务两次读取可能不同。

**官方参考：** [MySQL 8.4 Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) 和 [Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

## 什么是 MVCC？

### 先理解它要解决什么问题

假设一行余额原来是 `100`，事务 A 正在把它改成 `80`，但还没有提交。此时事务 B 查询余额，有两种简单但都不理想的处理方式：

1. 让 B 等待 A 提交，读到 `80`。数据新，但读请求被写事务阻塞。
2. 让 B 直接读取 A 尚未提交的 `80`。并发高，但如果 A 最后回滚，B 就发生了脏读。

MVCC（Multi-Version Concurrency Control，多版本并发控制）提供了第三种选择：**A 可以继续修改最新版，B 暂时读取修改前且对自己可见的旧版本 `100`**。因此，普通查询和写操作在很多情况下可以并发执行。

**大白话：** 数据库不是只保留“现在这一张账单”，还保留能还原旧账单的信息。查询先确定自己应该看哪个时间点，再从版本链里找到当时可见的版本。

### 一行数据如何形成版本链？

InnoDB 在聚簇索引记录中维护隐藏信息，其中理解 MVCC 最重要的是：

| 隐藏字段 | 专业含义 | 大白话 |
| --- | --- | --- |
| `DB_TRX_ID` | 最后插入或更新该记录的事务 ID | “这个版本是谁改的” |
| `DB_ROLL_PTR` | 指向 undo log 记录的回滚指针 | “上一个版本去哪里找” |
| `DB_ROW_ID` | InnoDB 生成聚簇索引时使用的隐藏行 ID | 没有合适主键时，InnoDB 自己补的行号 |

更新一行数据时，InnoDB 不会简单地把旧值彻底丢掉，而是：

1. 在 undo log 中记录足以还原修改前版本的信息。
2. 修改聚簇索引中的当前记录，并把 `DB_TRX_ID` 改为当前事务 ID。
3. 让当前记录的 `DB_ROLL_PTR` 指向对应的 undo log。
4. 多次更新后，当前记录和多条 undo log 记录通过回滚指针串成一条**版本链**。

undo log 并不一定保存一份完整行快照，而是保存重建旧版本所需的信息。它既用于事务回滚，也用于一致性读构造历史版本。

```text
当前版本 V3（trx_id = 120）
        │ DB_ROLL_PTR
        ▼
历史版本 V2（trx_id = 110）
        │ DB_ROLL_PTR
        ▼
历史版本 V1（trx_id = 90）
```

### Read View 是什么？

版本链解决了“旧版本存在哪里”，Read View 解决的是“当前事务应该看哪个版本”。可以把 Read View 理解为快照读创建时的一份**事务名单和边界记录**。

面试中常见的四个关键字段是：

| 字段 | 含义 | 判断作用 |
| --- | --- | --- |
| `creator_trx_id` | 创建 Read View 的事务 ID | 当前事务自己修改的数据可以看见 |
| `m_ids` | 创建快照时仍活跃、尚未提交的读写事务 ID 集合 | 版本来自这些事务时通常不可见 |
| `min_trx_id` | `m_ids` 中最小的事务 ID | 比它更早的版本通常已经提交，可见 |
| `max_trx_id` | 创建快照时系统下一个将分配的事务 ID | 大于等于它的事务在快照后才出现，不可见 |

不同资料或源码版本可能把两个边界称为 `up_limit_id`、`low_limit_id`。名称容易混淆，面试时重点说明它们分别代表“最早活跃事务”和“快照之后的事务边界”。

### Read View 怎样判断一个版本是否可见？

设当前检查版本的隐藏事务 ID 为 `DB_TRX_ID`，可以按以下顺序理解：

1. `DB_TRX_ID == creator_trx_id`：这是当前事务自己改出的版本，**可见**。
2. `DB_TRX_ID < min_trx_id`：生成快照前它通常已经提交，**可见**。
3. `DB_TRX_ID >= max_trx_id`：它在生成快照后才开始，**不可见**。
4. `min_trx_id <= DB_TRX_ID < max_trx_id`：检查 `m_ids`：
   - 在 `m_ids` 中，说明生成快照时仍未提交，**不可见**。
   - 不在 `m_ids` 中，说明生成快照前已经提交，**可见**。
5. 如果当前版本不可见，就沿 `DB_ROLL_PTR` 到 undo log 重建上一个版本，然后继续判断，直到找到可见版本或版本链结束。

### 用一个具体例子走完整流程

假设事务 T1 创建 Read View 时：

```text
creator_trx_id = 100
m_ids          = [110, 120]
min_trx_id     = 110
max_trx_id     = 130
```

此时某行数据的版本链是 `V3(120) → V2(110) → V1(90)`：

1. 先读当前版本 V3，`trx_id = 120` 在 `m_ids` 中，说明事务 120 当时尚未提交，V3 不可见。
2. 沿回滚指针找到 V2，`trx_id = 110` 也在 `m_ids` 中，V2 仍不可见。
3. 继续找到 V1，`trx_id = 90 < min_trx_id(110)`，说明它在快照生成前已经提交，V1 可见。
4. 查询最终返回 V1。这里不是返回“物理上最新的数据”，而是返回“对 T1 的快照而言正确的数据”。

![MVCC 快照读根据 Read View 判断版本可见性并沿 undo log 回溯的动态流程图](/.image/interview/persistence/mysql/mvcc-version-lookup.svg)

图中用一条示例版本链演示：V3、V2 对当前 Read View 不可见时，查询会沿 `roll_pointer` 回溯 undo log，直到找到已提交且可见的 V1。节点和连线会循环高亮；系统开启“减少动态效果”时自动显示为静态图。

### RC 和 RR 的区别到底在哪里？

MVCC 的版本链没有因为隔离级别不同而改变，主要区别在于**什么时候创建和复用 Read View**：

| 隔离级别 | Read View 使用方式 | 同一事务第二次普通查询 |
| --- | --- | --- |
| 读已提交（RC） | 每次一致性读创建新快照 | 可能看到其他事务刚提交的新版本 |
| 可重复读（RR） | 第一次一致性读创建快照，后续一致性读通常复用 | 继续按第一次快照读取，结果可重复 |

需要注意：普通 `BEGIN` 只表示事务开始，RR 下通常是**第一次快照读**时才建立 Read View；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 可以在事务开始时建立一致性快照。

### 快照读和当前读不要混在一起

| 类型 | 常见 SQL | 读取方式 | 是否加记录相关锁 |
| --- | --- | --- | --- |
| 快照读 / 一致性非锁定读 | 普通 `SELECT` | Read View + 版本链，读取可见版本 | 通常不加 |
| 当前读 / 锁定读 | `SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE` | 读取当前版本，必要时等待其他事务 | 加锁 |
| 写操作 | `UPDATE`、`DELETE` | 基于当前版本修改 | 加锁 |

所以，“RR 下永远只能看见旧数据”是错误的。普通 `SELECT` 按快照读；当前读和写操作为了保证修改正确性，会处理当前记录并加锁。把两种读取方式混在同一事务里，观察到的数据版本可能不同。

### MVCC 不等于完全没有锁

- MVCC 主要降低的是普通读与写之间的冲突，写与写之间仍然需要锁。
- `SELECT ... FOR UPDATE` 等当前读仍然需要锁。
- 长事务长期持有旧 Read View，会让仍可能被它读取的 update undo log 无法及时清理，导致版本链变长、undo 表空间膨胀。
- MVCC 保证的是隔离级别规定下的可见性，不自动保证余额不能为负、库存不能超卖等业务约束。

### 面试时可以这样回答

> MVCC 是 InnoDB 的多版本并发控制机制，目标是让普通读尽量不阻塞写。记录通过 `DB_TRX_ID` 标识版本的修改事务，通过 `DB_ROLL_PTR` 连接 undo log 形成版本链；快照读用 Read View 判断每个版本是否对当前事务可见，不可见就沿版本链向前查找。RC 每次快照读通常创建新 Read View，RR 通常复用第一次快照读建立的 Read View。MVCC 主要服务于快照读，当前读和写操作仍然需要加锁。

## InnoDB 有哪些常见的锁？

按粒度和用途，常见锁包括：

- **共享锁（S Lock）**：允许其他事务读取，不允许修改被锁数据。
- **排他锁（X Lock）**：不允许其他事务再获取冲突的共享锁或排他锁。
- **记录锁（Record Lock）**：锁定某条索引记录。
- **间隙锁（Gap Lock）**：锁定索引记录之间的间隙，不锁记录本身。
- **临键锁（Next-Key Lock）**：记录锁和间隙锁的组合。
- **意向锁**：表级标记，表明事务准备在某些行上加共享锁或排他锁。

InnoDB 的行锁是基于索引实现的。条件没有合适索引时，可能扫描并锁定更多记录，扩大锁冲突范围。

**大白话：** 行锁不是凭空锁住一行，而是沿着索引去找并锁住范围。没有合适索引，就像找一个人时只能把整层楼暂时管住，冲突自然更多。

## 什么是幻读？InnoDB 如何解决？

幻读是指同一事务按照相同条件再次查询时，发现其他事务新插入了符合条件的记录。

在 InnoDB 的可重复读级别中：

- **快照读**：通过 MVCC 读取一致性快照，后续查询通常看不到其他事务新提交的数据。
- **当前读**：通过记录锁、间隙锁和 next-key lock 锁住记录及相关范围，阻止其他事务在范围内插入数据。

需要注意，事务中混合使用快照读和当前读时，可能观察到不同的数据版本，业务设计仍需明确并发语义。

## 什么是死锁？如何处理？

死锁是多个事务互相等待对方持有的锁，形成循环依赖。常见处理方法：

1. 让多个事务按照相同顺序访问表和行。
2. 缩小事务范围，避免在事务中执行远程调用或耗时操作。
3. 为查询条件建立合适索引，减少扫描和加锁范围。
4. 将大事务拆小，但要保证业务一致性。
5. 应用捕获死锁异常后进行有限次数、带退避的重试。

InnoDB 能检测死锁，并回滚其中代价较小的事务。可以通过 `SHOW ENGINE INNODB STATUS` 等方式查看最近一次死锁信息。

**大白话：** 死锁像两个人在窄路上各自占着一头，又都等对方先让。数据库会让其中一方退回去；应用要能识别这个可重试错误，但不能无限重试。

## redo log、undo log 和 binlog 分别有什么作用？

- **redo log**：InnoDB 的物理日志，记录数据页的修改，用于崩溃恢复，保证事务持久性。
- **undo log**：记录数据修改前的版本，用于事务回滚和 MVCC。
- **binlog**：Server 层的逻辑日志，记录数据变更，用于主从复制、审计和基于时间点的数据恢复。

为了保证 redo log 和 binlog 的一致性，MySQL 内部事务提交会使用两阶段提交：先将 redo log 写入 prepare 状态，再写 binlog，最后将 redo log 标记为 commit。

![MySQL 事务提交中 undo log、redo log prepare、binlog 与 redo log commit 的关键顺序](/.image/interview/persistence/mysql/mysql-transaction-commit.svg)

**大白话：** `undo log` 是“后悔药”，用于回滚和读取旧版本；`redo log` 是 InnoDB 的“重启修复清单”；`binlog` 是给复制和审计看的“业务变更流水”。两阶段提交把 redo 和 binlog 绑在同一次提交中，避免一个说已提交、另一个没有记录。

## 为什么不建议使用 SELECT *？

1. 读取了不需要的列，增加磁盘、网络和序列化开销。
2. 更难使用覆盖索引，可能产生额外回表。
3. 表结构新增字段后，接口返回、对象映射和内存占用可能发生意外变化。
4. 可读性较差，无法直接看出查询真正依赖的字段。

因此，业务查询应明确列名；只有临时排查或确实需要整行数据时再考虑使用 `SELECT *`。

## COUNT(*)、COUNT(1) 和 COUNT(列) 有什么区别？

- `COUNT(*)`：统计满足条件的行数，不忽略整行。
- `COUNT(1)`：对每行统计常量 `1`，效果通常与 `COUNT(*)` 相同。
- `COUNT(列)`：只统计该列不为 `NULL` 的行数。

在现代 MySQL 的 InnoDB 中，`COUNT(*)` 通常经过专门优化，可读性也最好。不要为了所谓性能固定改成 `COUNT(1)`；应根据是否需要忽略 `NULL` 选择写法。

## 大表新增索引或字段要注意什么？

1. 评估 DDL 算法是否支持 `INSTANT` 或 `INPLACE`，以及是否会重建表。
2. 关注元数据锁（MDL）。未提交的长事务可能让 DDL 长时间等待，并阻塞后续请求。
3. 在业务低峰执行，提前评估磁盘空间、执行时间、复制延迟和回滚方案。
4. 超大表可以使用经过验证的在线变更工具，但要评估触发器、外键和主从环境限制。
5. 变更前清理长事务，变更中持续监控锁等待、延迟和资源使用情况。

## MySQL 主从复制的基本原理是什么？

主库将数据变更写入 binlog；从库的接收线程读取主库 binlog 并写入 relay log，再由应用线程重放 relay log 中的事件。并行复制可以提高重放速度。

异步复制下，主库提交成功不代表从库已经同步完成，因此可能出现复制延迟或主库故障时的数据丢失风险。读写分离还需要处理“写后立刻读”的一致性问题，例如关键查询走主库、等待复制位点或使用具备一致性保证的架构。

**大白话：** 主库像总账，从库像抄账员。异步复制时总账刚写完，抄账员可能还没抄到；所以用户刚下单就去从库查，可能暂时查不到，关键读需要回主库或等待同步确认。

## 如何设计一张高并发业务表？

需要结合访问模式设计，而不是只看字段：

1. 选择短且稳定的主键，避免无序大主键造成频繁页分裂。
2. 根据高频查询、排序和更新场景设计少而有效的索引。
3. 选择合适的数据类型和长度，金额使用 `DECIMAL` 或最小货币单位整数，避免浮点误差。
4. 明确唯一约束、非空约束、默认值以及状态流转规则。
5. 控制单次事务的数据量和持锁时间，设计幂等键防止重复写入。
6. 先通过索引、SQL 和冷热数据治理解决问题，再根据实际容量考虑分区或分库分表。
7. 建立慢查询、连接数、锁等待、复制延迟和容量增长监控。
