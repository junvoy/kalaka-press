# MySQL 面试题

## MySQL 的逻辑架构是怎样的？

MySQL 可以分为 **Server 层** 和 **存储引擎层**：

- **Server 层**：负责连接管理、权限校验、SQL 解析、优化和执行，并提供函数、存储过程、触发器等能力。
- **存储引擎层**：负责数据的存储和读取。常用的 InnoDB 支持事务、行级锁、外键和崩溃恢复。

一条查询 SQL 通常会经过：连接器 → 解析器 → 优化器 → 执行器 → 存储引擎。

## InnoDB 和 MyISAM 有什么区别？

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行级锁为主，也支持表级锁 | 表级锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持 | 能力较弱 |
| 索引组织 | 聚簇索引 | 非聚簇索引 |
| 适用场景 | 高并发读写、需要事务 | 以读为主且不需要事务的旧系统 |

MySQL 5.5 之后，InnoDB 是默认存储引擎，业务系统通常优先选择 InnoDB。

## 为什么 InnoDB 推荐使用自增主键？

InnoDB 使用主键组织聚簇索引，叶子节点按主键顺序存放完整行数据。自增主键具有以下优点：

1. 新数据通常追加到索引末尾，减少页分裂和数据移动。
2. 整数比较速度快，索引占用空间小。
3. 二级索引的叶子节点会保存主键值，主键越短，二级索引越节省空间。

随机 UUID 会让插入位置分散，更容易产生页分裂和索引碎片。如果业务必须使用 UUID，可以考虑将有序 ID 作为物理主键，并对业务 UUID 建唯一索引。

## MySQL 索引为什么使用 B+ 树？

B+ 树适合磁盘和范围查询：

1. 非叶子节点只保存键和子节点指针，单页可以容纳更多键，树的高度更低，磁盘 I/O 更少。
2. 所有数据都在叶子节点，查询性能更稳定。
3. 叶子节点通过链表相连，范围查询和排序可以顺序扫描。
4. 相比哈希索引，B+ 树既支持等值查询，也支持范围、排序和最左前缀匹配。

## 聚簇索引和二级索引有什么区别？

- **聚簇索引**：叶子节点保存完整行数据。InnoDB 通常使用主键作为聚簇索引，一张表只能有一个。
- **二级索引**：叶子节点保存索引列和对应的主键值。一张表可以有多个二级索引。

通过二级索引查询非索引列时，需要先得到主键，再到聚簇索引查询完整数据，这个过程叫作 **回表**。

## 什么是覆盖索引？

查询需要的列全部包含在某个索引中，无须回表，这个索引就称为覆盖索引。

例如存在联合索引 `idx_user_status(user_id, status)`：

```sql
SELECT user_id, status
FROM orders
WHERE user_id = 1001;
```

该查询可以直接从联合索引返回结果。覆盖索引能够减少随机 I/O，但不应为了覆盖所有查询而创建过宽的索引，否则会增加存储空间和写入成本。

## 什么是最左前缀原则？

联合索引会按照索引列从左到右排序。假设索引为 `(a, b, c)`，通常可以支持：

- `a`
- `a, b`
- `a, b, c`
- `a` 等值匹配后对 `b` 或 `c` 做范围、排序等操作

如果跳过最左侧的 `a`，通常不能利用该联合索引完成高效定位。设计联合索引时，一般把区分度较高、经常作为等值条件的列放在前面，同时结合实际查询、排序和分组需求判断。

## 哪些情况可能导致索引失效或无法充分使用？

常见情况包括：

1. 联合索引不满足最左前缀原则。
2. 对索引列进行函数计算或表达式运算，如 `DATE(create_time) = '2026-08-21'`。
3. 隐式类型转换，例如字符串列使用数字条件比较。
4. 使用以通配符开头的模糊查询，如 `LIKE '%keyword'`。
5. 对索引列使用不利于范围定位的条件，如部分 `OR`、`NOT IN`、`!=` 查询。
6. 优化器判断全表扫描成本更低，例如返回数据占表中比例过高。

是否真正使用索引，应以 `EXPLAIN` 和实际执行统计为准，不能只凭 SQL 形式判断。

## 如何分析 EXPLAIN 的结果？

重点关注以下字段：

- `type`：访问方式。常见性能趋势为 `const` > `ref` > `range` > `index` > `ALL`。
- `possible_keys`：优化器可能选择的索引。
- `key`：实际使用的索引。
- `key_len`：使用的索引长度，可辅助判断联合索引使用了哪些列。
- `rows`：预计需要扫描的行数。
- `filtered`：经过条件过滤后预计保留的百分比。
- `Extra`：补充信息，如 `Using index`、`Using temporary`、`Using filesort`。

`Using filesort` 不一定表示使用磁盘排序，`Using temporary` 也不一定必然很慢。分析时要结合扫描行数、数据量、SQL 延迟以及 `EXPLAIN ANALYZE` 的实际执行信息。

## 一条慢 SQL 应该如何排查和优化？

可以按以下顺序处理：

1. 通过慢查询日志、监控或链路追踪定位 SQL、耗时和调用频率。
2. 使用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 查看访问方式、扫描行数、索引和排序情况。
3. 检查索引是否缺失、冗余，联合索引顺序是否匹配查询条件。
4. 减少返回列和扫描行数，避免 `SELECT *`，尽量使用覆盖索引。
5. 优化深分页、复杂子查询、不必要的排序和大事务。
6. 确认是否存在锁等待、连接池耗尽、磁盘 I/O 或 Buffer Pool 命中率低等问题。
7. 在接近生产的数据量和分布下验证优化效果，并关注写入成本和其他 SQL 的回归。

## 深分页为什么慢？如何优化？

```sql
SELECT *
FROM orders
ORDER BY id
LIMIT 1000000, 20;
```

MySQL 需要先定位并跳过前 1000000 行，再返回 20 行；如果查询包含非索引列，还可能发生大量回表。

常用优化方式是基于上一页最后一个排序键做游标分页：

```sql
SELECT *
FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

如果必须跳转到指定页，可以先通过覆盖索引查询主键，再与原表关联。排序键应稳定且唯一，例如使用 `(create_time, id)` 避免同一时间值导致数据重复或遗漏。

## 什么是事务的 ACID？

- **原子性（Atomicity）**：事务中的操作要么全部成功，要么全部回滚，主要由 undo log 保证。
- **一致性（Consistency）**：事务执行前后，数据满足业务约束和完整性规则，是事务机制共同作用的结果。
- **隔离性（Isolation）**：并发事务之间互不干扰，主要通过锁和 MVCC 实现。
- **持久性（Durability）**：事务提交后，数据不会因系统故障而丢失，主要由 redo log 保证。

## MySQL 有哪些事务隔离级别？

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交（READ UNCOMMITTED） | 可能 | 可能 | 可能 |
| 读已提交（READ COMMITTED） | 避免 | 可能 | 可能 |
| 可重复读（REPEATABLE READ） | 避免 | 避免 | 可能 |
| 串行化（SERIALIZABLE） | 避免 | 避免 | 避免 |

InnoDB 默认使用可重复读。它通过 MVCC 保证快照读的可重复性，并通过 next-key lock 等机制处理当前读中的幻读问题。隔离级别越高，并发能力通常越低，应根据一致性要求选择。

## 什么是 MVCC？

MVCC（多版本并发控制）让读写操作在多数情况下不互相阻塞。InnoDB 的实现主要依赖：

- 记录中的隐藏事务 ID 和回滚指针。
- undo log 中保存的历史版本。
- Read View 判断某个数据版本对当前事务是否可见。

在读已提交级别下，通常每次快照读都会生成新的 Read View；在可重复读级别下，事务中的第一次快照读通常生成 Read View，后续快照读复用它。

普通 `SELECT` 通常是快照读；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 等属于当前读，会读取最新版本并按需要加锁。

## InnoDB 有哪些常见的锁？

按粒度和用途，常见锁包括：

- **共享锁（S Lock）**：允许其他事务读取，不允许修改被锁数据。
- **排他锁（X Lock）**：不允许其他事务再获取冲突的共享锁或排他锁。
- **记录锁（Record Lock）**：锁定某条索引记录。
- **间隙锁（Gap Lock）**：锁定索引记录之间的间隙，不锁记录本身。
- **临键锁（Next-Key Lock）**：记录锁和间隙锁的组合。
- **意向锁**：表级标记，表明事务准备在某些行上加共享锁或排他锁。

InnoDB 的行锁是基于索引实现的。条件没有合适索引时，可能扫描并锁定更多记录，扩大锁冲突范围。

## 什么是幻读？InnoDB 如何解决？

幻读是指同一事务按照相同条件再次查询时，发现其他事务新插入了符合条件的记录。

在 InnoDB 的可重复读级别中：

- **快照读**：通过 MVCC 读取一致性快照，后续查询通常看不到其他事务新提交的数据。
- **当前读**：通过记录锁、间隙锁和 next-key lock 锁住记录及相关范围，阻止其他事务在范围内插入数据。

需要注意，事务中混合使用快照读和当前读时，可能观察到不同的数据版本，业务设计仍需明确并发语义。

## 什么是死锁？如何处理？

死锁是多个事务互相等待对方持有的锁，形成循环依赖。常见处理方法：

1. 让多个事务按照相同顺序访问表和行。
2. 缩小事务范围，避免在事务中执行远程调用或耗时操作。
3. 为查询条件建立合适索引，减少扫描和加锁范围。
4. 将大事务拆小，但要保证业务一致性。
5. 应用捕获死锁异常后进行有限次数、带退避的重试。

InnoDB 能检测死锁，并回滚其中代价较小的事务。可以通过 `SHOW ENGINE INNODB STATUS` 等方式查看最近一次死锁信息。

## redo log、undo log 和 binlog 分别有什么作用？

- **redo log**：InnoDB 的物理日志，记录数据页的修改，用于崩溃恢复，保证事务持久性。
- **undo log**：记录数据修改前的版本，用于事务回滚和 MVCC。
- **binlog**：Server 层的逻辑日志，记录数据变更，用于主从复制、审计和基于时间点的数据恢复。

为了保证 redo log 和 binlog 的一致性，MySQL 内部事务提交会使用两阶段提交：先将 redo log 写入 prepare 状态，再写 binlog，最后将 redo log 标记为 commit。

## 为什么不建议使用 SELECT *？

1. 读取了不需要的列，增加磁盘、网络和序列化开销。
2. 更难使用覆盖索引，可能产生额外回表。
3. 表结构新增字段后，接口返回、对象映射和内存占用可能发生意外变化。
4. 可读性较差，无法直接看出查询真正依赖的字段。

因此，业务查询应明确列名；只有临时排查或确实需要整行数据时再考虑使用 `SELECT *`。

## COUNT(*)、COUNT(1) 和 COUNT(列) 有什么区别？

- `COUNT(*)`：统计满足条件的行数，不忽略整行。
- `COUNT(1)`：对每行统计常量 `1`，效果通常与 `COUNT(*)` 相同。
- `COUNT(列)`：只统计该列不为 `NULL` 的行数。

在现代 MySQL 的 InnoDB 中，`COUNT(*)` 通常经过专门优化，可读性也最好。不要为了所谓性能固定改成 `COUNT(1)`；应根据是否需要忽略 `NULL` 选择写法。

## 大表新增索引或字段要注意什么？

1. 评估 DDL 算法是否支持 `INSTANT` 或 `INPLACE`，以及是否会重建表。
2. 关注元数据锁（MDL）。未提交的长事务可能让 DDL 长时间等待，并阻塞后续请求。
3. 在业务低峰执行，提前评估磁盘空间、执行时间、复制延迟和回滚方案。
4. 超大表可以使用经过验证的在线变更工具，但要评估触发器、外键和主从环境限制。
5. 变更前清理长事务，变更中持续监控锁等待、延迟和资源使用情况。

## MySQL 主从复制的基本原理是什么？

主库将数据变更写入 binlog；从库的接收线程读取主库 binlog 并写入 relay log，再由应用线程重放 relay log 中的事件。并行复制可以提高重放速度。

异步复制下，主库提交成功不代表从库已经同步完成，因此可能出现复制延迟或主库故障时的数据丢失风险。读写分离还需要处理“写后立刻读”的一致性问题，例如关键查询走主库、等待复制位点或使用具备一致性保证的架构。

## 如何设计一张高并发业务表？

需要结合访问模式设计，而不是只看字段：

1. 选择短且稳定的主键，避免无序大主键造成频繁页分裂。
2. 根据高频查询、排序和更新场景设计少而有效的索引。
3. 选择合适的数据类型和长度，金额使用 `DECIMAL` 或最小货币单位整数，避免浮点误差。
4. 明确唯一约束、非空约束、默认值以及状态流转规则。
5. 控制单次事务的数据量和持锁时间，设计幂等键防止重复写入。
6. 先通过索引、SQL 和冷热数据治理解决问题，再根据实际容量考虑分区或分库分表。
7. 建立慢查询、连接数、锁等待、复制延迟和容量增长监控。
