# 消息队列面试题

消息队列（Message Queue，MQ）通过异步通信连接生产者与消费者，常用于系统解耦、流量削峰和耗时任务异步化。它不是“接入后就不会丢消息”的保险箱：可靠性需要生产端、Broker、消费端和业务数据共同保证。

这页按“**面试一句话 → 专业原理 → 大白话 → 边界或源码**”组织。先讲通用机制，再以官方发布标签 [`rocketmq-all-5.5.0`](https://github.com/apache/rocketmq/releases/tag/rocketmq-all-5.5.0) 的实现作为源码主线；RabbitMQ、Kafka 和 RocketMQ 的术语与能力不同，不要把某个产品的配置当成所有 MQ 的统一结论。

## 基础架构

### 1. 为什么使用消息队列？它带来了什么代价？

**面试一句话：** MQ 主要解决异步处理、系统解耦和流量削峰，但同步调用会变成最终一致，系统还要承担重复、乱序、积压、重试和运维复杂度。

生产者只需要把事件可靠交给 Broker，不必等待每个下游执行完；消费者按照自己的处理能力拉取或接收消息，短时流量峰值可以先在队列中缓冲。

**大白话：** MQ 像餐厅的取餐叫号系统。顾客下单后不用站在后厨等，后厨也能按产能逐单处理；但小票可能重复、排队过长或无人认领，所以必须有编号、重做和异常处理机制。

**边界或误区：** 必须立即得到结果的登录校验、余额确认等同步环节，不能只为了“解耦”就改成异步。MQ 能缓冲流量，不能凭空提高数据库和第三方接口的处理上限。

### 2. 一条消息从生产到消费经历什么？

**面试一句话：** 生产者选择 Topic 和队列后发送消息，Broker 完成存储并返回发送结果；消费者处理业务后确认成功，失败消息按策略重试，超过上限后进入死信队列。

![消息从生产者发送、Broker 存储到消费确认、重试和死信处理的完整生命周期](/.image/interview/middleware/mq/message-lifecycle.svg)

发送成功只表示消息到达了约定的 Broker 存储阶段，不表示下游业务已经完成。消费成功也应以业务状态提交为准，不能在业务执行前提前确认。

**大白话：** 快递员揽件成功不等于收件人已经签收。包裹先进入中转站，再派送给收件人；派送失败会重试，多次失败后进入异常件区并告警。

#### 源码解析：Broker 写入与消费结果是两个阶段

RocketMQ 5.5.0 的 [`CommitLog.asyncPutMessage`](https://github.com/apache/rocketmq/blob/rocketmq-all-5.5.0/store/src/main/java/org/apache/rocketmq/store/CommitLog.java) 会设置存储时间、计算消息体 CRC、编码并把消息追加到 CommitLog。消费侧则由 [`ConsumeMessageConcurrentlyService`](https://github.com/apache/rocketmq/blob/rocketmq-all-5.5.0/client/src/main/java/org/apache/rocketmq/client/impl/consumer/ConsumeMessageConcurrentlyService.java) 调用业务监听器，再处理成功或稍后重试的返回状态。两段源码说明“Broker 收到消息”和“业务消费成功”不是同一件事。

### 3. Topic、MessageQueue、Consumer Group 和 Broker 怎么理解？

**面试一句话：** Topic 是消息的逻辑分类，MessageQueue 是 Topic 下承载并行与顺序的逻辑队列，Consumer Group 表示一组共同分担消费进度的消费者，Broker 负责消息存储和投递。

同一 Consumer Group 在集群消费模式下共同消费一份消息，不同 Consumer Group 可以分别消费同一 Topic。MessageQueue 的数量通常决定一个消费组可并行处理的上限之一。

**大白话：** Topic 像报纸栏目，MessageQueue 像栏目下的多条分拣通道，Consumer Group 像同一家配送团队，Broker 则是保存报纸并负责分发的站点。两家不同团队可以各拿一整份，同一团队内部会分工。

**边界或误区：** RabbitMQ 常用 Exchange、Queue、Binding 描述路由，Kafka 常用 Topic、Partition、Consumer Group。术语不能机械互换，但都要回答“消息如何分类、如何分片、谁共享消费进度”。

### 4. 同步、异步和单向发送怎样选择？

**面试一句话：** 同步发送等待 Broker 结果、异常处理最直接；异步发送通过回调获得结果、吞吐更高但要管理并发和回调失败；单向发送不等待确认，可靠性要求最低。

关键业务消息通常使用同步或带可靠回调的异步发送，并记录消息 Key、发送结果、耗时和失败原因。客户端重试必须使用稳定的业务事件 ID，因为超时不代表 Broker 一定没有收到消息。

```java
Message message = new Message(
    "order-events",
    "created",
    orderJson.getBytes(StandardCharsets.UTF_8)
);
message.setKeys(eventId);

SendResult result = producer.send(message, 3_000);
if (result.getSendStatus() != SendStatus.SEND_OK) {
  pendingEventRepository.record(eventId, orderJson);
  throw new MessageSendException(eventId);
}
```

**大白话：** 同步发送像寄件后当场等回执；异步发送像留下联系方式，回执稍后通知；单向发送像把信投入没有查询能力的信箱。业务越关键，越不能只管“发出去”而不管结果。

**边界或误区：** 示例只能处理发送结果，不能解决“订单已提交但应用还没来得及发消息”的数据库与 MQ 双写问题；这类问题要使用第 16 题的 Outbox 或第 17 题的事务消息方案。

## 可靠投递

### 5. 怎样避免消息在生产端、Broker 和消费端丢失？

**面试一句话：** 生产端要确认发送结果并可靠重试，Broker 要持久化并配置副本与刷盘策略，消费端要在业务成功后确认，同时保留告警、重放和补偿路径。

可以按三个故障点回答：生产者在超时或网络异常时记录待重试事件；Broker 根据可靠性目标选择同步刷盘、异步刷盘和复制策略；消费者失败时返回失败状态，不推进确认进度。

**大白话：** 防丢不能只看中转站有没有仓库，还要看寄件人是否拿到回执、中转站是否有备份、收件人是否真正签收。三个环节缺一个都可能找不到包裹。

**边界或误区：** 同步刷盘和多副本会增加写入延迟，也不能覆盖应用数据库与发消息之间的原子性。可靠性应先定义可接受的数据丢失窗口、恢复时间和成本，再选择策略。

### 6. ACK、Offset 与重复消费是什么关系？

**面试一句话：** ACK 或 Offset 表示消费进度；若业务已提交但确认尚未成功，Broker 会认为消息没有完成并再次投递，因此至少一次投递天然要求消费端幂等。

RocketMQ 并发消费会先调用业务 `MessageListenerConcurrently`，再由 `processConsumeResult` 根据 `CONSUME_SUCCESS` 或 `RECONSUME_LATER` 更新进度或发回重试。网络超时、客户端宕机和 Rebalance 都可能扩大“业务成功但进度未提交”的窗口。

**大白话：** 你已经把账记进系统，但在勾掉待办之前电脑断电了。重启后待办仍显示未完成，于是同一笔账会再处理一次。

**边界或误区：** 不要为了减少重复而在业务执行前提前 ACK，这会把“可能重复”换成“业务失败却永不重投”。重复通常比丢失更容易通过业务幂等修复。

### 7. 消费端怎样实现幂等？

**面试一句话：** 消费者应使用稳定的业务事件 ID，通过数据库唯一约束、状态机或版本号识别重复，并把幂等记录与核心业务更新放在同一个本地事务中。

![消息消费通过事件唯一键、同一事务更新业务并在确认丢失后安全重投的幂等流程](/.image/interview/middleware/mq/idempotent-consume.svg)

```java
@Transactional
public void handle(OrderPaidEvent event) {
  boolean first = processedEventRepository.tryInsert(event.eventId());
  if (!first) {
    return;
  }

  orderRepository.markPaid(
      event.orderId(),
      event.paidAt()
  );
}
```

`processed_event.event_id` 必须有唯一约束，`tryInsert` 在键已存在时返回 `false`。幂等记录与订单更新处于同一事务，避免只写入去重记录却没有完成业务。

**大白话：** 每张业务小票都有唯一编号。第一次看到就登记并处理，再看到同一编号就直接告诉 MQ“已经做过”，不能把同一订单重复扣款或重复发货。

**边界或误区：** 只在 Redis 设置一个短期 Key 可能遇到过期、淘汰或“Key 已写但数据库事务失败”。外部支付、短信等无法纳入数据库事务的副作用，还需要请求幂等号、状态查询或补偿机制。

### 8. 最多一次、至少一次和恰好一次有什么区别？

**面试一句话：** 最多一次可能丢但不重投，至少一次尽力不丢但可能重复；端到端恰好一次需要消息系统、状态存储和外部副作用共同协调，业务中通常通过至少一次加幂等实现“效果上的一次”。

| 语义 | 失败时的典型行为 | 业务代价 |
| --- | --- | --- |
| 最多一次 | 不确定时不重投 | 可能丢消息 |
| 至少一次 | 不确定时再次投递 | 可能重复 |
| 恰好一次 | 原子协调消息与状态 | 范围受限、成本更高 |

**大白话：** 最多一次是“宁可漏送也不重复”，至少一次是“宁可多送也别漏送”，恰好一次则要求每个参与者都能证明同一件事只生效一次。

**边界或误区：** Kafka 的事务或某个客户端的 Exactly Once 配置，只覆盖其声明的处理边界；数据库写入、HTTP 调用、短信和人工操作不会自动获得端到端恰好一次。

### 9. 顺序消息如何实现？

**面试一句话：** 顺序消息通常以订单号等业务键选择同一 MessageQueue，并由消费者对该队列串行处理，从而保证同一业务键的局部顺序；全局顺序会明显牺牲吞吐和可用性。

生产端和消费端必须共同保证顺序：相同业务键稳定路由到同一队列，消费失败时不能跳过旧消息继续提交新进度。业务状态机还应拒绝过期状态，例如“已退款”不能被迟到的“已支付”覆盖。

**大白话：** 同一个订单的消息必须进入同一条排队通道，并按先来后到处理；不同订单可以走不同通道并行，不需要所有订单只排一条长队。

**边界或误区：** 扩容、Rebalance、失败重试和生产端并发都可能影响顺序。能用状态版本号解决的问题，不要一开始就要求昂贵的全局顺序。

## 故障与容量

### 10. 消费失败后怎样设计重试？

**面试一句话：** 重试要区分临时故障与永久故障，配置最大次数和退避间隔，并配合超时、限流、熔断与可观测性，避免无限重试形成放大流量。

连接超时、短暂限流等可恢复错误适合指数或分级退避；参数非法、业务状态不允许等永久错误应尽快终止自动重试。每次尝试应记录消息 ID、业务键、异常类型、重试次数和下一次时间。

**大白话：** 门暂时锁住可以隔一会儿再敲，地址写错就不该一直敲。重试不是越快越好，下游已经过载时连续重试只会让门口更拥堵。

**边界或误区：** RocketMQ 的消费重试用于恢复消费失败，不应当作业务流程跳转或限流工具。官方策略在超过最大次数后会把消息转入 DLQ，而不是永久循环。[消费重试说明](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)

### 11. 死信队列（DLQ）是什么？怎样安全重放？

**面试一句话：** DLQ 保存超过重试上限、过期或被拒绝的消息，是可观测、可修复、可审计的故障清单；修复根因后才能按业务键和速率安全重放。

完整的 DLQ 治理包括告警、查询工具、失败原因、原始消息与版本、责任人、修复记录和重放结果。重放前应确认消费者已幂等，并评估旧消息是否仍符合当前业务状态。

**大白话：** DLQ 是异常件仓库，不是垃圾桶。地址修好后可以重新派送，但必须先确认收件人没有已经收到，也不能把几万件异常包裹一次性重新塞回正常通道。

**边界或误区：** 进入 DLQ 不代表问题处理完成。没有告警、查询和重放流程的死信队列，只是把线上故障隐藏得更久。

### 12. 消息积压怎样排查？日常监控哪些指标？

**面试一句话：** 先比较生产速率、消费速率和消费延迟，再结合失败率、处理耗时、队列热点、实例状态及下游容量定位根因；扩容前必须确认队列并行度和下游承载能力。

建议按“现象 → 瓶颈 → 恢复 → 复盘”排查：确认积压量和最老消息年龄是否持续增长；检查消费者是否存活、是否频繁重试或 Rebalance；分析数据库、缓存和外部接口耗时；恢复后补齐阈值、限流和容量基线。

**大白话：** 排队变长时先看是客人突然变多、窗口关了、每单处理变慢，还是所有人都挤在同一个窗口。盲目增加窗口，可能让后厨先被压垮。

**边界或误区：** 只监控消息数量不够，还应关注生产/消费 TPS、Consumer Lag、最老消息年龄、成功率、重试/DLQ 数、P95/P99 处理耗时和下游错误率。

### 13. 什么是 Rebalance？为什么会引发抖动或重复？

**面试一句话：** Rebalance 是消费组成员或队列集合变化后重新分配 MessageQueue 的过程；旧消费者撤销队列与新消费者接管之间可能发生暂停、重复投递和局部顺序影响。

消费者上线、下线、网络超时或 Topic 队列变化都可能触发重新分配。接管者会从已提交的消费进度继续，如果旧消费者业务已成功但进度未提交，同一消息就可能再次被处理。

**大白话：** 配送团队换班时要重新分配片区。上一班已经送到但还没登记的包裹，下一班可能再送一次；如果人员频繁进出，大家会一直忙着分片区而不是送货。

**边界或误区：** 不要通过频繁重启消费者解决积压。应先减少非必要扩缩容、设置合理的超时与优雅停机，并确保消费幂等和状态提交边界正确。

### 14. RocketMQ 如何存储消息？Broker 高可用怎样理解？

**面试一句话：** RocketMQ 将消息顺序追加到 CommitLog，再通过 ConsumeQueue 等逻辑索引支持按 Topic 和队列消费；刷盘与副本策略共同影响发送确认、数据丢失窗口和故障切换能力。

顺序追加有利于提高磁盘写吞吐，消费索引只保存定位 CommitLog 所需的信息。同步刷盘更关注落盘确认，异步刷盘延迟更低；副本复制负责机器故障场景，两者解决的问题不同。

**大白话：** CommitLog 像按到达顺序装订的总账，ConsumeQueue 像不同栏目对应的目录。刷盘是把内存里的内容真正写进账本，副本是再准备一份账本防机器损坏。

**边界或误区：** “已经持久化”不等于任何故障下都零丢失。面试中应说明使用何种刷盘、复制和切换策略，以及它们对延迟、吞吐和数据窗口的影响。

### 15. 延迟消息适合哪些场景？

**面试一句话：** 延迟消息让消息在指定时间之后才可被消费，适合订单超时关闭、延迟通知和重试调度；它通常不是毫秒级高精度定时器，消费者执行前仍要校验最新业务状态。

延迟时间只决定“最早何时可见”，实际执行时间还受 Broker 调度、积压和消费者处理能力影响。订单关闭等动作要用条件更新，确保订单已经支付时不会被迟到消息关闭。

**大白话：** 延迟消息像设置稍后提醒，但提醒响起不代表事情还需要做。收到“关闭订单”提醒时，要先看订单是不是已经支付。

**边界或误区：** 海量、超长周期且要求可修改、可取消的定时任务，应评估专用调度系统或时间轮方案，不能把所有定时需求都塞给 MQ。

## 一致性与选型

### 16. 本地事务与发消息怎样用 Outbox 保持一致？

**面试一句话：** Outbox 在同一个数据库事务中写入业务数据和待发送事件，再由独立投递器可靠发送并更新状态，从而把数据库与 MQ 的双写问题转换为数据库内的单写事务和可重试投递。

![业务数据与 Outbox 在同一事务提交后由投递器可靠发送并由消费者幂等处理的流程](/.image/interview/middleware/mq/outbox-delivery.svg)

```java
@Transactional
public void createOrder(CreateOrderCommand command) {
  orderRepository.insert(command.toOrder());
  outboxRepository.insert(
      OutboxEvent.pending(
          command.eventId(),
          "order-created",
          command.toJson()
      )
  );
}

public void publish(OutboxEvent event) {
  producer.send(toMessage(event));
  outboxRepository.markSent(event.id());
}
```

投递器要批量锁定待处理记录、限制重试速率并记录发送结果。如果消息已发出但 `markSent` 失败，事件会再次发送，所以消费端仍必须幂等。

**大白话：** 创建订单时，同时在同一本数据库账本里写一张“待发通知”。后台人员不断扫描这些通知，发成功再盖章；即使中途停机，没盖章的通知还在，可以继续发送。

**边界或误区：** Outbox 提供最终一致，不提供数据库与 MQ 的瞬时强一致。还要处理表膨胀、并发抢占、失败告警、归档和重复发送。

### 17. RocketMQ 事务消息与事务回查是什么？

**面试一句话：** 生产者先发送对消费者不可见的 Half Message，Broker 写入成功后执行本地事务，再提交 Commit 或 Rollback；状态未知时 Broker 回查生产者的本地事务结果。

![RocketMQ 事务消息从 Half Message、本地事务到提交、回滚和 Broker 回查的流程](/.image/interview/middleware/mq/transaction-message-check.svg)

正常路径是 Half Message → 本地事务 → Commit → 消息对消费者可见；若本地事务失败则 Rollback。进程宕机或二阶段响应丢失时，Broker 会扫描待确认事务消息并调用生产者的事务检查器。

**大白话：** Broker 先把消息放进“待确认区”，等生产者办完本地业务后再决定正式发布还是作废。如果生产者没回话，Broker 会回来问“这笔业务到底成功没有”。

#### 源码解析：回查负责消除未知状态

RocketMQ 5.5.0 的 [`TransactionalMessageServiceImpl.check`](https://github.com/apache/rocketmq/blob/rocketmq-all-5.5.0/broker/src/main/java/org/apache/rocketmq/broker/transaction/queue/TransactionalMessageServiceImpl.java) 扫描事务 Half Topic，结合 Half Offset 和 Op Offset 识别待确认消息，再触发回查；`commitMessage` 与 `rollbackMessage` 根据 CommitLog Offset 定位原 Half Message。

**边界或误区：** 事务消息保证的是生产者本地事务与消息发布之间的最终一致，不保证下游业务自动成功。事务检查器必须能根据本地事务记录幂等查询状态，消费者仍需重试和幂等。[官方事务消息说明](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)

### 18. RabbitMQ、Kafka 和 RocketMQ 怎样选型？

**面试一句话：** 选型应先明确吞吐、端到端延迟、消息模型、顺序、回放、延迟与事务需求，再结合运维能力选择；RabbitMQ 路由灵活，Kafka 擅长高吞吐事件流，RocketMQ 对业务消息能力支持较完整。

| 维度 | RabbitMQ | Kafka | RocketMQ |
| --- | --- | --- | --- |
| 典型优势 | Exchange 路由灵活、协议生态成熟 | 高吞吐、分区日志、事件回放 | 顺序、延迟、事务和重试等业务能力 |
| 常见场景 | 业务路由、任务分发、集成 | 日志、埋点、流式数据平台 | 订单、交易、通知等业务事件 |
| 重点评估 | 队列与路由治理 | 分区、Lag、保留周期 | Topic/队列、消费组、事务与运维 |

**大白话：** RabbitMQ 像路线灵活的快递分拣中心，Kafka 像能长期保存并反复读取的高速流水带，RocketMQ 像为订单类业务准备了较多标准处理能力的消息平台。

**边界或误区：** 产品标签只是初筛，不能脱离实际压测、故障演练、团队经验和总成本。面试回答应先给业务约束，再解释为什么候选产品满足这些约束。
