# 第一性原理学习地图

技术名词会变化，系统反复面对的基本事实却很稳定：内存有限、网络不可靠、并发会竞争、节点会独立失败、模型输出具有概率性。本站采用马斯克在访谈中对第一性原理的通俗解释：不因为“行业一直这样做”就接受现成答案，而是把问题还原为尽可能确定的基本事实，再从这些事实向上重新构造方案。

这不等于把每篇文章都追溯到物理学。技术学习中的“基本事实”必须可观察、可验证，并且已经低到足以重新推导当前机制；无法验证的行业说法只能标为假设，不能充当推理起点。

## 第一性原理怎样用于技术学习？

| 层次 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 目标 | 真正要得到什么结果，而不是要使用什么技术 | 订单事件最终被处理且不能重复扣款 |
| 基本事实 | 哪些现象有证据，暂时无法继续拆解 | 网络会超时，进程会在任意步骤退出 |
| 硬约束 | 时间、空间、权限和业务规则限制了什么 | 数据库与 Broker 不能共享一个普通本地事务 |
| 假设与类比 | 哪些只是惯例、产品宣传或“大家都这样做” | “用了 MQ 就不会丢消息” |
| 重新构造 | 只根据事实和目标，最少需要什么机制 | 持久化、确认、重试、幂等、告警和补偿 |
| 证伪 | 改变前提或注入故障，推导是否仍成立 | 业务提交后 ACK 前宕机，结果能否保持正确 |

只有走完这条链路，才去看 Java、Spring、RocketMQ 或 Agent 框架怎样实现。源码用于验证推导，不是替代推导。

第一次系统学习，从本页按基本问题向下走；已经知道要查某个框架或组件时，使用[技术索引](./technology-index)。两种入口指向同一份正文，不重复维护答案。

## 1. 数据如何表示、组织和访问？

任何程序都要在有限内存和有限时间内保存、查找、修改与遍历数据。数组、链表、哈希表和树不是需要孤立背诵的结构，而是对访问速度、写入成本、顺序、内存和并发约束的不同取舍。

- [Java 基础](./java/basic)：类型、对象、相等性和异常怎样表达业务规则。
- [Java 集合](./java/collections)：从操作需求推导数组、链表、哈希表、树和队列。
- [现代 Java](./java/modern-java)：怎样用不可变数据、函数和流水线组织变换。

## 2. 程序如何执行、并发和管理资源？

CPU、内存和线程都是有限资源。多个任务共享状态时会产生竞态、可见性和顺序问题；任务增长时还必须限制线程、排队和拒绝，而不是无限创建执行单元。

- [并发正确性](./java/concurrency)：原子性、可见性、有序性与锁怎样约束共享状态。
- [多线程与线程池](./java/multithreading)：任务怎样调度、排队、取消和隔离。
- [JVM](./java/jvm)：代码怎样加载、执行、分配内存、回收并接受诊断。

## 3. 请求与信息如何流动？

跨进程通信必须面对分层协议、有限带宽、缓冲、阻塞和连接生命周期。Web 框架和 Netty 都建立在这些更基础的网络与 I/O 机制之上。

- [网络与 I/O](./web/io-network)：字节、缓冲、连接、HTTP 和 NIO 怎样协作。
- [Netty](./web/netty)：事件循环和 Channel 怎样组织高并发网络程序。
- [Spring 与 Spring Boot](./spring/question)：请求怎样进入应用、完成依赖协作并形成响应。

## 4. 状态如何保存并保持正确？

数据系统既要快速读取和写入，又要在并发、宕机和重复请求下保持业务约束。事务、日志、索引、缓存和对象映射分别解决状态生命周期中的不同问题。

- [MySQL](./mysql/question)：索引、事务、锁、MVCC 和日志怎样保证性能与正确性。
- [Redis](./redis/question)：内存数据结构、过期、淘汰和缓存一致性怎样取舍。
- [MyBatis](./persistence/mybatis)：对象、SQL、连接和事务边界怎样衔接。

## 5. 多节点如何协作并应对部分失败？

只要一次业务跨越网络，就可能出现超时、重复、乱序和局部成功。分布式系统的核心不是消灭这些现象，而是定义权威状态、不变量和收敛路径。

- [消息队列](./middleware/mq)：异步协作怎样处理持久化、确认、重试、幂等和积压。
- [分布式系统设计](./distributed/question)：一致性、可用性、幂等、事务和容错怎样权衡。
- [微服务治理](./microservices/question)：服务发现、RPC、限流、熔断和网关怎样控制调用关系。
- [配置、调度与数据集成](./integration/question)：异构任务怎样可重复执行、追踪和恢复。

## 6. 系统如何发布、观测和恢复？

代码能运行不等于系统可交付。测试、发布、日志、指标、追踪、告警与补偿工具共同回答三个问题：现在是否正确、哪里出了问题、怎样安全恢复。

- [设计模式与工程实践](./engineering/question)：怎样控制变化、验证行为和降低耦合。
- [可观测性与交付](./operations/question)：怎样发布、发现故障、定位根因并恢复服务。
- [车联网与实时通信](./iot/question)：把通用机制放进长连接与设备状态场景验证。
- [Vue 3 与运营平台协作](./frontend/question)：前后端怎样围绕状态、接口和错误边界协作。

## 7. 不确定的 AI 如何安全参与确定性业务？

大模型擅长理解非结构化输入和生成候选方案，但概率输出不能直接成为资金、权限或订单的事实来源。可控 AI 系统必须把模型能力放在确定性状态、规则、工具权限和人工责任边界之内。

- [AI 基础概念](./ai/fundamentals/question)：模型、Prompt、RAG、工具和 Agent 的能力边界。
- [AI Agent 工程化](./ai/agent/question)：状态机、幂等、人工复核、审计与评测怎样控制执行。
- [OpenAI SDK 与 Responses API](./ai/sdk/question)：模型与工具之间的协议和运行循环。
- [LangChain 与 LangGraph](./ai/langchain/question)：状态、持久化和编排怎样落地。
- [AI 应用案例](./ai/cases/question)：用真实项目与通用方案验证工程边界。

## 一章应该怎样学？

1. 先定义真正想要的结果，不预设 ArrayList、MQ、状态机等具体方案。
2. 写出“通常怎么做”，逐条标记其中的事实、假设、惯例和类比。
3. 去掉技术名词，把问题拆到可观察、可验证的基本事实与硬约束。
4. 只使用这些事实，从零构造能保护目标不变量的最小机制。
5. 再与现有实现和源码对照，解释它为何这样设计，又增加了哪些工程优化。
6. 改变前提或注入故障，主动寻找能推翻结论的反例。
7. 最后完成章节自测，并尝试用 30 秒和 3 分钟两种长度表达。
