# 微服务治理面试题

本章对应简历中的 Spring Cloud、Dubbo、Nacos 和 Sentinel。重点是说明服务拆开后怎样发现彼此、控制故障和保证配置变更安全。

## 服务通信与治理

### 1. Dubbo 和 HTTP REST 怎么选？

**面试一句话：** Dubbo 适合内部服务间高性能 RPC 调用，通常通过接口和注册中心管理；HTTP REST 更通用、调试与跨语言协作方便。应按调用边界、治理能力和团队约定选择，而不是只看性能。

内部高频调用还要设置超时、重试和异常语义。超时不代表服务端没有执行，写操作必须先设计幂等。

### 2. Nacos 的服务注册与发现怎样工作？

**面试一句话：** 服务实例启动后向 Nacos 注册自身地址并持续心跳；消费者订阅服务名对应的实例列表，在本地缓存后负载均衡调用。实例异常或心跳超时会被标记或摘除。

注册中心解决“去哪里调用”，不解决“调用必然成功”。客户端仍必须设置连接、读取和总体超时，并准备重试或熔断。

### 3. Nacos 配置中心怎样实现动态刷新？

**面试一句话：** 客户端通过长轮询或推送感知配置版本变化，拉取新内容并通知需要刷新的组件；动态配置应有命名空间、分组、灰度、审计与回滚，不应把所有配置都无差别热更新。

数据库连接池、线程池等资源配置变更前，要确认组件是否支持安全刷新以及正在执行任务的影响。

### 4. 配置版本、快照和回滚分别解决什么？

**面试一句话：** 版本记录说明当前使用哪一份配置，快照保存可恢复的历史内容，回滚把指定版本重新发布；三者共同让配置变更可追溯、可验证和可恢复。

简历中的“录入—审批—发布—验证—回滚”本质上是把配置当作受治理的生产变更，而不是一段可直接覆盖的文本。

### 5. 什么是多租户数据隔离？

**面试一句话：** 多租户隔离是让不同客户或业务主体的数据、权限和配置互不越界；常见实现有独立库、独立 schema、共享表加租户列，以及请求上下文路由。

无论采用哪种方式，都不能只靠前端传参。服务端需要在认证后的可信上下文中注入租户条件，并防止缓存 Key、消息和异步任务串租户。

### 6. Sentinel 中的限流、熔断和降级有什么区别？

**面试一句话：** 限流控制进入系统的请求量，熔断在依赖错误率或慢调用异常时暂时快速失败，降级返回可接受的简化结果；Sentinel 用规则和统计指标帮助实现这些保护。

规则阈值要来自压测与业务容量。核心写入接口不能随意返回“成功”的降级结果，应明确提示稍后重试或走可靠补偿。

### 7. 为什么要做服务隔离？

**面试一句话：** 隔离通过独立线程池、连接池、队列或资源配额，防止一个慢依赖耗尽所有资源并拖垮其他功能。

例如批量对账、实时接口和通知任务不应共用无边界线程池；隔离后还要监控队列积压、拒绝次数和下游延迟。

### 8. 什么是 API 网关？

**面试一句话：** API 网关位于客户端和服务之间，统一处理路由、认证、限流、灰度、跨域和审计等横切能力；它不应承载大量核心业务编排。

网关转发的用户身份与关联 ID 要可信地传递给下游，敏感内部接口不应仅靠“路径不公开”保护。

### 9. 一次微服务调用失败，怎样定位？

**面试一句话：** 先通过关联 ID 确认失败发生在网关、调用方、网络还是被调方，再检查超时、错误率、实例健康、线程池、连接池与依赖指标，最后根据根因修复并验证。

不要把所有异常都归因为 Nacos 或网络。调用链、结构化日志和指标要能回答“哪个接口、哪个实例、哪个下游、从何时开始”。

### 10. 灰度发布为什么重要？

**面试一句话：** 灰度发布先让少量实例或流量使用新版本，观察错误率、延迟和业务指标后再逐步扩大，能降低配置或代码变更的爆炸半径。

灰度期间应保持接口与消息兼容，并准备快速回滚开关；数据库变更优先采用新旧版本都能工作的向前兼容方案。
