# JVM 怎样执行、管理内存并暴露故障

JVM 的价值不只是“运行字节码”和“自动 GC”。它必须在有限的 CPU、内存和暂停预算内，安全地加载不完全可信的 class 文件，持续执行程序，并在资源不足时留下可诊断证据。

## 目标：不预设 HotSpot 的现成答案

我们要解决的问题是：对象数量和生命周期由运行时输入决定，而物理内存有限；程序还要求动态加载、快速执行和可控暂停。怎样构造一个既遵守 Java 语义，又能回收空间和定位故障的运行系统？

学习后应当能够：

1. 从生命周期与共享范围推导 JVM 运行时数据区域。
2. 从“对象何时不再有用不可预知”推导可达性分析和 GC。
3. 从“回收必须观察一致对象图”推导安全点与 STW。
4. 区分 JVM 规范、HotSpot 21 实现和具体收集器策略。
5. 从现象选择 GC 日志、线程转储、堆转储、JFR 等证据，而不是先调参数。

## 拆掉现成答案

| 常见说法 | 分类 | 被隐藏的条件 |
| --- | --- | --- |
| 对象都在堆上 | 入门模型 | 语言不承诺物理布局，JIT 还可能做标量替换等优化 |
| 方法区就是元空间 | 混淆规范与实现 | 方法区是 JVMS 的逻辑区域，Metaspace 是 HotSpot 的实现选择 |
| 年轻代一定复制、老年代一定整理 | 历史类比 | 收集器的堆组织、回收集合与算法组合不同 |
| Full GC 一定最慢 | 无条件结论 | 必须比较收集器、堆规模、回收原因和实际暂停数据 |
| G1 能保证停顿时间 | 错误假设 | `MaxGCPauseMillis` 是软目标，分配速率和存活集可能让目标失效 |
| ZGC 没有 STW | 错误绝对化 | 它把大量工作并发化，但仍存在短暂的暂停阶段 |
| OOM 就把 `-Xmx` 调大 | 治标惯例 | 泄漏、分配洪峰、直接内存、元空间和线程耗尽的根因不同 |
| CPU 高就是死循环 | 单因果假设 | 热点计算、锁自旋、序列化和频繁 GC 都可能产生同一表象 |

## 从基本事实重新构造

### 从生命周期与共享范围推导运行时区域

执行一条方法调用至少需要当前位置、参数、局部变量、中间计算结果和被调用方法的信息；对象又可能跨越一次方法调用，被多个线程共享。把所有数据放在同一块区域，会让生命周期管理和并发隔离都变复杂。

因此 JVMS 定义了不同职责的逻辑区域：

![JVM 运行时内存区域](/.image/interview/java/jvm/jvm-memory.svg)

| 区域 | 共享范围 | 从基本事实推导出的职责 |
| --- | --- | --- |
| 程序计数器 | 线程私有 | 每个执行流必须知道下一条 JVM 指令 |
| JVM 栈 | 线程私有 | 方法调用天然形成后进先出的栈帧生命周期 |
| 本地方法栈 | 线程私有 | native 调用需要承载实现相关状态 |
| 堆 | JVM 共享 | 对象和数组可能跨方法、跨线程存活 |
| 方法区 | JVM 共享 | 类结构、运行时常量池和方法代码被多个实例复用 |

“线程私有”不等于不会出错：递归过深可能导致 `StackOverflowError`，无法继续扩展栈也可能 OOM。“共享”也不等于对象字段自动线程安全。

JVMS 只定义逻辑责任，不规定方法区必须放在哪里、对象头有多少字节或堆必须连续。HotSpot 的 Metaspace、TLAB 和压缩对象指针都属于版本实现。

### 从有限内存推导分配、泄漏与回收

对象创建速度可能瞬间高于回收速度，物理内存又存在上限，因此运行系统至少需要：

1. 找到可用空间并完成分配。
2. 判断哪些对象仍可能被程序使用。
3. 回收或复用不再可达的空间。
4. 在无法满足分配时明确失败。

GC 只能回收“不再可达”的对象。如果业务已经不需要对象，但静态集合、监听器、线程或 ThreadLocal 仍保留引用，从 JVM 视角它仍然活着，这就是 Java 中常见的逻辑内存泄漏。

短期创建大量对象属于高分配速率；长期持有无用对象属于泄漏。两者都可能表现为 GC 频繁和 OOM，却需要不同修复。

### 从不可预知生命周期推导可达性分析

仅靠引用计数无法处理环：两个对象互相引用，但系统其他部分已经无法到达它们。更稳健的最小模型是从一组必然存活的入口出发遍历对象图：

```text
GC Roots
  ├─ 活跃线程栈中的引用
  ├─ 类静态字段持有的引用
  ├─ JNI 引用
  └─ JVM 内部必要引用
        ↓ 沿引用边遍历
      可达对象保留；不可达对象才有回收资格
```

强、软、弱、虚引用并不是四档缓存优先级：

- **强引用**：只要仍从 Roots 可达，就不会因普通 GC 被回收。
- **软引用**：回收策略受内存压力和实现影响，不适合构造确定性缓存。
- **弱引用**：只剩弱引用时可以被回收；`ThreadLocalMap` 的弱 Key 并不能自动释放强 Value。
- **虚引用**：不能取得对象，通常配合引用队列观察回收后的资源管理事件。

### 从存活率与碎片推导回收算法

回收空间有三个基本动作：识别存活对象、释放死亡对象、决定是否移动存活对象。由此得到常见算法：

| 算法 | 机制 | 主要代价 | 更有利的条件 |
| --- | --- | --- | --- |
| 标记—清除 | 标记存活，回收其余空间 | 可能产生碎片 | 移动成本高或可由其他机制管理空闲块 |
| 标记—复制 | 把存活对象复制到另一空间 | 需要复制和预留空间 | 存活对象较少 |
| 标记—整理 | 移动存活对象并压缩空闲区 | 更新引用和移动对象有成本 | 需要连续空间且存活率较高 |

“大多数新对象很快死亡”是许多业务负载中的经验观察，不是语言定律。分代收集利用这一局部性，把不同年龄对象放入不同回收策略中：

![对象从年轻代进入老年代的简化流程](/.image/interview/java/jvm/generational-gc.svg)

Minor、Major 和 Full GC 是工具与收集器语境中的常用名称，并非所有收集器都给它们完全相同的含义。排障时必须同时记录收集器、回收原因和实际涉及区域。

### 从一致对象图推导安全点与 STW

若应用线程一边修改引用，收集器一边判断对象是否存活，可能观察到互相矛盾的对象图。最简单正确方案是暂停全部应用线程再完成所有回收工作，但暂停会直接进入用户延迟。

现代收集器因此在正确性约束内把更多阶段并发执行，并使用写屏障、记忆集或着色状态记录并发变化；某些阶段仍需在安全点暂停应用线程。结论是：

- STW 是暂停应用线程的机制，不等于某一种 GC。
- 并发回收减少的是需要暂停完成的工作，不等于零暂停。
- 暂停目标必须由 P99/P999、最大暂停和业务超时共同定义。

### 从目标函数推导 G1 与 ZGC 的选择

收集器没有脱离负载的排名。选择需要同时考虑吞吐量、最大暂停、CPU 预算、堆大小、分配速率和 JDK 版本。

![G1 Region 与回收方式](/.image/interview/java/jvm/g1-regions.svg)

G1 把堆划分成 Region，以回收收益和停顿目标选择回收集合；年轻代与老年代在逻辑上存在，但物理区域无需连续。它以额外的记忆集、并发工作和预测误差换取更可控的分批回收。

JDK 21 中 ZGC 更侧重低暂停，把大量昂贵工作并发完成，也会消耗 CPU 和内存余量。不能只看产品介绍中的暂停级别；必须在相同流量、堆大小和服务目标下比较吞吐、CPU、最大暂停与尾延迟。

### 从动态依赖推导类加载、连接与初始化

JVM 不能在启动时假设所有类都已经存在，因为类可能来自应用、模块、生成代码或自定义来源。它必须先定位 class 表示，再验证结构与类型安全，建立符号关系，最后在需要时执行初始化逻辑。

![Java 类从加载到卸载的生命周期](/.image/interview/java/jvm/class-loading.svg)

稳定的阶段模型是：

1. **加载**：找到 class 表示并创建运行时类。
2. **连接**：验证、准备，按 JVM 允许的时机解析符号引用。
3. **初始化**：执行类初始化方法，为显式静态初始化赋值。

准备阶段为类变量建立默认初始状态，初始化阶段才执行代码中的显式赋值。JVM 规范允许解析在连接后的不同时间发生，因此不能把某个实现的“加载—验证—准备—解析—初始化”时间线当作所有细节都严格串行。

常见 `ClassLoader.loadClass` 实现优先检查已加载类，再委托父加载器，最后尝试自己查找。双亲委派避免核心类型被应用随意替换，也减少重复定义；SPI、应用服务器、模块层和热部署可能采用不同委派关系。类型身份由类的二进制名和定义它的类加载器共同决定。

### 从热点分布推导解释执行、JIT 与逃逸分析

程序刚启动时，不知道哪些路径最常执行。把所有代码都做高成本优化会拉长启动时间，只解释执行又会牺牲长期吞吐。因此 HotSpot 可以先收集运行画像，再把热点代码编译为优化机器码，并在假设失效时去优化。

逃逸分析尝试判断对象是否逃出方法或线程，为标量替换、锁消除等优化提供依据。它不提供“对象一定分配在栈上”的语言保证；优化是否发生取决于代码形态、编译层级和具体 JVM。

### 从症状不唯一推导证据链

同一表象可能对应多个根因，所以调优必须先定义目标和收集证据：

| 现象 | 第一批证据 | 常见分叉 |
| --- | --- | --- |
| 延迟尖峰 | 请求指标、GC 日志、JFR | GC 暂停、锁竞争、外部依赖 |
| 堆持续上升 | GC 后占用、堆转储、引用链 | 缓存增长、监听器、ThreadLocal |
| CPU 持续高 | 多次线程转储、JFR 热点、GC CPU | 死循环、热点计算、自旋、频繁 GC |
| OOM | 完整错误、堆转储、NMT、线程数 | 堆、Metaspace、直接内存、本地线程 |

调大堆可能减少 GC 频率，也可能增加占用和最长回收时间；切换收集器可能改善暂停，也可能消耗更多 CPU。没有基线和同等负载对比，就不能证明调优有效。

## 固定版本的实现与源码验证

稳定边界与固定实现分别取证：

- [JVMS 21 第 2 章：JVM 结构](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html)：运行时数据区域和帧的规范。
- [JVMS 21 第 5 章：加载、连接与初始化](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html)：类生命周期的规范。
- [OpenJDK `jdk-21-ga`](https://github.com/openjdk/jdk/tree/jdk-21-ga)：固定 HotSpot 21 源码入口。
- [HotSpot G1 源码目录](https://github.com/openjdk/jdk/tree/jdk-21-ga/src/hotspot/share/gc/g1)：Region、并发标记和回收策略的实现入口。
- [`classLoader.cpp`](https://github.com/openjdk/jdk/blob/jdk-21-ga/src/hotspot/share/classfile/classLoader.cpp)：HotSpot 类加载基础设施入口。
- [`escape.cpp`](https://github.com/openjdk/jdk/blob/jdk-21-ga/src/hotspot/share/opto/escape.cpp)：C2 逃逸分析实现入口。

源码只证明 HotSpot 21 如何兑现规范。其他 JVM 可以使用不同对象布局、编译器和收集器。

## 最小实验：让运行时留下证据

### 实验一：观察初始化时机

```java
class Parent {
    static final int CONSTANT = 42;
    static { System.out.println("Parent initialized"); }
}

public class InitDemo {
    public static void main(String[] args) {
        System.out.println(Parent.CONSTANT);
    }
}
```

编译后用 `javap -c -v` 检查常量是否内联，再把字段改成运行时计算，比较初始化输出。它可以证伪“引用一个类的任何字段都会触发初始化”。

### 实验二：区分高分配与泄漏

分别运行“持续创建短命对象”和“把对象放入静态 List”的小程序，并开启：

```bash
java -Xms128m -Xmx128m -Xlog:gc* AllocationDemo
```

比较每次 GC 后的基线占用。短命对象造成高频分配但基线可回落；强引用列表会让存活集持续上升。

### 实验三：CPU 高不能靠单次快照定因

对同一进程间隔采集多份线程转储，验证热点线程是否持续停留在相似调用栈；再用 JFR 对照 CPU 样本与 GC 事件。单次 `jstack` 只提供瞬时证据。

## 验证与证伪

| 假设 | 注入或改变条件 | 证伪信号 |
| --- | --- | --- |
| 所有对象都必须真实分配在堆中 | 运行可被标量替换的微基准并检查编译日志 | 语言层无法依赖固定物理布局 |
| 引用计数足以回收对象 | 构造仅互相引用但无 Root 可达的对象环 | 对象仍可被可达性 GC 回收 |
| G1 停顿目标等于 SLA 保证 | 提高存活集和分配速率 | 实际最大暂停可超过软目标 |
| 并发收集没有 STW | 对照 GC 日志中的暂停事件 | 仍能观察短暂停顿阶段 |
| OOM 只来自堆 | 创建大量线程或直接缓冲区 | 错误区域与堆泄漏不同 |
| 一次线程转储足以定位 CPU | 连续采样比较调用栈 | 单次热点可能只是瞬时执行 |

## 工程取舍与失败边界

- 更大的堆能提供分配余量，也增加内存成本，并可能改变回收周期和最长恢复时间。
- 更低暂停通常需要更多并发 GC 工作和 CPU 余量，可能牺牲吞吐。
- 自定义类加载器提供隔离与热部署，也容易造成类身份冲突和卸载失败。
- 堆转储与 JFR 很有价值，但可能包含敏感数据；线上采集要控制权限、磁盘和保留周期。
- GC 调优不能修复无界缓存、错误所有权或下游阻塞。
- JVM 指标正常也不能证明业务正确，仍需结合请求、数据库和外部依赖证据。

## 理解自测与面试表达

以下 16 个标题保持原样。回答时从约束和证据出发，不把内存图或收集器名当成结论。

### 1. JVM 运行时内存区域有哪些？

**正文定位：** 生命周期与共享范围。**反事实追问：** 方法区为什么不能直接等同于 Metaspace？**表达骨架：** 3 分钟按“线程私有—共享—规范与实现边界—常见失败”回答。

### 2. 堆和栈有什么区别？

**正文定位：** 对象跨调用存活与栈帧 LIFO。**反事实追问：** “对象都在堆上”为何不能当物理布局保证？**表达骨架：** 30 秒比较共享、内容、生命周期和错误类型。

### 3. 什么情况下会发生内存泄漏？

**正文定位：** 业务无用但仍可达。**反事实追问：** 高分配速率一定是泄漏吗？**表达骨架：** 3 分钟讲可达性、GC 后基线、引用链和修复所有权。

### 4. JVM 怎样判断对象可以被回收？

**正文定位：** 从 GC Roots 遍历对象图。**反事实追问：** 两个互相引用的对象为什么仍可回收？**表达骨架：** 30 秒讲 Roots、可达性和“有资格”不等于立即回收。

### 5. 什么是 Minor GC、Major GC 和 Full GC？

**正文定位：** 分代与工具语境。**反事实追问：** 为什么不能跨收集器用同一含义解释 Major GC？**表达骨架：** 30 秒先声明收集器和日志语境，再说明涉及区域与暂停。

### 6. 什么是 Stop The World？

**正文定位：** 一致对象图。**反事实追问：** 并发收集器为什么仍可能暂停？**表达骨架：** 30 秒说明暂停谁、为何需要以及业务关注指标。

### 7. G1 垃圾收集器有什么特点？

**正文定位：** Region、回收集合与软停顿目标。**反事实追问：** 分配速率超过回收能力时目标还能保证吗？**表达骨架：** 3 分钟按“问题—机制—代价—失效条件”回答。

### 8. 类加载过程有哪些阶段？

**正文定位：** 加载、连接与初始化。**反事实追问：** 解析一定在初始化前一次完成吗？**表达骨架：** 3 分钟区分规范阶段、准备默认值和初始化代码。

### 9. 什么是类加载器的双亲委派？

**正文定位：** 动态依赖与类型身份。**反事实追问：** SPI 和热部署为什么可能改变委派关系？**表达骨架：** 30 秒讲先委托、核心类型保护、重复定义和例外场景。

### 10. JVM 调优的基本思路是什么？

**正文定位：** 症状不唯一与证据链。**反事实追问：** 没有基线时如何证明参数修改有效？**表达骨架：** 3 分钟按“目标—证据—根因—单变量修改—同负载验证—回滚”回答。

### 11. 强引用、软引用、弱引用和虚引用有什么区别？

**正文定位：** 不同可达性语义。**反事实追问：** ThreadLocal Key 是弱引用为何仍会泄漏 Value？**表达骨架：** 3 分钟按“能否取得对象—回收条件—引用队列—适用边界”回答。

### 12. 标记-清除、标记-复制和标记-整理有什么区别？

**正文定位：** 存活率、复制成本与碎片。**反事实追问：** 为什么不能把算法和某个年代永久绑定？**表达骨架：** 30 秒比较动作、空间和适用负载。

### 13. G1、ZGC 等垃圾收集器应该怎样选择？
