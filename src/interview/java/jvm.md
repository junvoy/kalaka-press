# JVM：内存、GC、类加载与线上排查

JVM 面试题最容易把“规范概念、HotSpot 实现、某个收集器行为、线上经验”混成一套口诀。本章以 Java SE 21 规范说明稳定边界，以 OpenJDK 21 和对应工具说明可验证实现。

## 内存与对象

### 1. JVM 运行时数据区域有哪些？

**直接回答：** JVMS 定义程序计数器、JVM 栈、堆、方法区、运行时常量池和本地方法栈等区域；其中程序计数器和 JVM 栈等按线程拥有，堆和方法区通常由所有线程共享。

![JVM 运行时内存区域](/.image/interview/java/jvm/jvm-memory.svg)

- JVM 栈由栈帧组成，保存局部变量、操作数栈、动态链接和返回信息。
- 堆主要承载由 JVM 管理的对象和数组，是 GC 重点管理的区域。
- 方法区是规范概念，保存类结构、方法与字段信息等；HotSpot 的 Metaspace 是其实现的一部分，不能简单写成恒等式。
- 直接内存、线程栈和本地库等也会消耗进程内存，不能只看 `-Xmx`。

### 2. 堆和栈有什么区别？

**直接回答：** JVM 栈服务于一次次方法调用，栈帧通常随调用进入和退出；堆承载跨方法、跨线程可共享的对象，由垃圾收集器根据可达性管理。局部变量在栈帧中，不代表它引用的对象也一定“在栈上”。

JIT 可能通过标量替换等优化消除对象分配，但这是运行时优化结果，不是 Java 源码层“new 一定在堆”或“局部对象一定在栈”的简单二选一。

### 3. 对象创建大致经历什么过程？

**直接回答：** 执行 `new` 时，JVM 先确保目标类已加载并初始化到允许状态，再为对象分配空间、初始化默认值、设置对象元数据，随后执行构造器相关字节码。实际分配可能使用线程本地分配缓冲区（TLAB）降低竞争。

构造器返回不一定意味着对象从未提前暴露：如果在构造期间把 `this` 注册到共享位置，其他线程可能看到未完成状态。对象头布局、指针压缩和 TLAB 策略属于 HotSpot 与启动参数相关的实现细节。

### 4. 什么情况下会发生内存泄漏？

**直接回答：** Java 内存泄漏不是“对象永远无法释放”，而是业务已经不再需要的对象仍被 GC Roots 间接引用，导致堆占用持续增长。常见来源有无界缓存、监听器未注销、ThreadLocal 未清理、类加载器链和队列积压。

泄漏与高分配率不同：高分配可能频繁 GC 后回落，泄漏的存活集通常随时间上升。应比较多时间点的 GC 日志、堆使用和 heap dump，而不是只看一次内存快照。

### 5. JVM 怎样判断对象可以回收？

**直接回答：** 主流 JVM 使用可达性分析：从 GC Roots 出发沿引用图遍历，不可达对象才成为回收候选。引用计数不能独立处理循环引用，因此不能作为 HotSpot 一般对象存活判断的完整解释。

常见 Roots 包括活动线程栈中的引用、类静态字段、JNI 引用和 JVM 内部引用。不可达也不等于“此刻立即回收”，具体回收时机取决于收集器和内存压力。

### 6. 强、软、弱、虚引用有什么区别？

**直接回答：** 强引用正常阻止回收；软引用在内存压力下可能被清理；弱引用在相应可达性处理时更积极地被清理；虚引用不能用来取得对象，通常与 ReferenceQueue 配合跟踪回收后的资源清理时机。

软引用不适合作为可预测的业务缓存策略，因为何时清理由 JVM 决定；业务缓存仍需要明确容量、淘汰、命中率和加载保护。虚引用也不能替代 try-with-resources 对外部资源进行确定性关闭。

## 垃圾收集

### 7. 标记-清除、复制和标记-整理有什么区别？

**直接回答：** 标记-清除标出存活对象后回收空闲区域，可能产生碎片；复制把存活对象搬到另一块区域，分配简单但要预留空间；标记-整理让存活对象向一侧移动，减少碎片但搬移成本更高。

收集器会根据存活率、停顿目标、堆大小和并发能力组合这些思想，不应把整个 JVM 描述成只使用一种算法。

### 8. 分代收集为什么有效？Minor、Major 和 Full GC 怎么区分？

**直接回答：** 很多工作负载中，大量对象存活时间短，少量对象长期存活；分代让收集器更频繁地处理年轻对象、较少扫描长期存活区域。Minor GC 常指年轻代收集，Full GC 常指更完整的堆与相关区域处理；“Major GC”的含义在不同工具和收集器中并不统一。

![对象从年轻代进入老年代的简化流程](/.image/interview/java/jvm/generational-gc.svg)

术语不是排障证据。实际分析要看收集器名称、GC 日志中的 cause、回收集合、暂停阶段、前后占用与持续时间。对象晋升阈值和区域布局也可能因收集器而不同。

### 9. 什么是 Stop The World？

**直接回答：** STW 表示 JVM 在某些阶段让应用线程到达安全点并暂停，以获得可处理的一致状态。并发收集器可以把大量工作与应用并发执行，但通常仍有短暂暂停阶段。

安全点不是“每条字节码都能随时停”。达到安全点过慢、线程过多、根扫描和对象搬移都可能影响暂停。评估 GC 不能只看总吞吐，还要看 P95/P99 暂停和业务尾延迟。

### 10. G1 垃圾收集器的基本思路是什么？

**直接回答：** G1 把堆划分为许多 Region，按年轻代或老年代角色使用；它并发标记全堆存活情况，再选择收益较高的 Region 组成回收集合，希望在暂停目标下优先回收更多垃圾。

![G1 Region 与回收方式](/.image/interview/java/jvm/g1-regions.svg)

G1 仍可能发生 Young、Mixed 和更严重的回收阶段，暂停目标是软目标而非 SLA。大对象、晋升压力、记忆集成本、并发标记跟不上分配速度，都可能造成退化。

### 11. G1、ZGC 等收集器怎么选？

**直接回答：** 先明确最大堆、吞吐目标、可接受暂停、CPU 预算和 JDK 版本，再用真实负载比较。G1 是 JDK 21 常见通用选择；ZGC 把大部分工作并发化，适合非常重视低停顿的较大堆，但会付出额外 CPU、内存和并发工作成本。

选择收集器不是背“谁最好”。小堆批处理可能更重吞吐，大堆在线服务可能更重尾延迟；还要考虑容器内存限制、对象分配模式和运维团队能否观察、回滚。

## 类加载与执行优化

### 12. 类加载过程有哪些阶段？

**直接回答：** 类的生命周期通常描述为加载、连接、初始化；连接又包含验证、准备和解析。加载得到 class 二进制并创建对应运行时结构，连接检查并准备类型，初始化执行类初始化方法。

![Java 类从加载到卸载的生命周期](/.image/interview/java/jvm/class-loading.svg)

访问编译期常量不一定触发声明类初始化；数组类型的创建也不等于初始化元素类型。可以用 `javap -c -v` 看常量是否内联，再通过静态初始化日志验证触发条件。

### 13. 什么是双亲委派？为什么要打破？

**直接回答：** 常见 ClassLoader 在加载类时先委托父加载器，父级无法完成时再尝试自己查找，这有助于避免核心类型被应用重复定义并保持类型边界。它是 ClassLoader 实现惯例与安全模型的一部分，不是所有加载场景都只能沿一棵严格父子树工作。

SPI、应用服务器、插件系统和模块隔离可能需要线程上下文类加载器或自定义查找顺序。打破委派要明确命名冲突、类型身份、卸载和安全边界；同名 class 由不同加载器加载后，JVM 可把它们视为不同类型。

### 14. 什么是 JIT 和逃逸分析？

**直接回答：** JIT 根据运行时热点和类型信息，把频繁执行的字节码编译为本地代码，并可做内联、去虚化等优化；逃逸分析判断对象是否可能被方法或线程之外观察，为标量替换、锁消除等优化提供依据。

这些优化不是源码语义保证，可能因分支、调用形态、JVM 参数和运行阶段变化。性能结论应在足够预热后用 JMH 或生产 profile 验证，不能用一次 `System.nanoTime()` 循环证明。

## 调优与故障排查

### 15. JVM 调优的基本思路是什么？

**直接回答：** 先定义业务目标并建立证据链，再定位 CPU、分配、存活集、GC、锁或 I/O 中哪个资源先饱和；优先修复对象生命周期和业务算法，最后才调整堆、收集器和参数。

推荐顺序：

1. 明确吞吐、P99 延迟、错误率和资源预算。
2. 保留 GC 日志、JFR、线程转储、堆转储和系统指标。
3. 对齐异常时间线，建立“症状—资源—代码栈”的因果假设。
4. 一次只改变一个关键变量，用相同负载比较并准备回滚。

“把 Xmx 调大”可能减少 GC 频率，也可能增加最长回收时间和容器风险；参数不是脱离目标的优化。

### 16. 常见 OOM 有哪些？怎样排查？

**直接回答：** OOM 只是分配失败结果，可能来自 Java heap space、Metaspace、Direct buffer memory、unable to create native thread、GC overhead limit 等。先保留原始错误文本，再按对应资源取证。

- 堆 OOM：分析 heap dump 的大对象、支配树和引用链。
- Metaspace：关注类数量、类加载器是否无法卸载和动态生成类。
- 直接内存：核对 NIO 分配、池化释放和进程 RSS。
- 无法创建本地线程：核对线程数、栈大小、进程限制和容器内存。

不要在内存紧张的生产进程里盲目执行高开销转储；应提前配置 OOM dump、日志路径、磁盘容量和应急开关。

### 17. Java 进程 CPU 很高时怎样排查？

**直接回答：** 先确认是整个进程、某个线程、GC 还是系统层 CPU 异常；再把高 CPU 线程与线程转储中的 Java 栈对应，并用 JFR 或 profiler 持续采样。单次栈只能证明那一刻在哪里，不能证明长期热点。

常见原因包括忙循环、频繁 GC、锁自旋、序列化/正则热点和流量突增。修复后要对比相同负载下的 CPU、吞吐与尾延迟，避免只是把成本转移到数据库或网络。

## 面试表达与最小实验

### 30 秒回答骨架

> 我先区分 JVM 规范和 HotSpot 实现。运行时区域解释数据放在哪里，可达性决定对象是否仍被需要，收集器再围绕吞吐、停顿和内存成本做取舍。线上调优不先背参数，而是用 GC 日志、JFR、线程转储和堆转储建立证据链，再验证修改是否改善业务指标。

### 两个最小实验

```bash
javap -c -v InitDemo
java -Xms128m -Xmx128m -Xlog:gc* AllocationDemo
```

第一个实验对比编译期常量和运行时计算字段，观察类初始化触发差异；第二个实验用固定小堆观察分配速率、回收前后占用和暂停，区分“分配很多”与“存活集不断增长”。
