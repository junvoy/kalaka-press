# Java 程序怎样表达并运行

Java 基础不是一组互不相关的语法题。本章先移除“JVM 天生跨平台”“面向对象就是三句话”等现成答案，从硬件执行、类型检查、对象身份和资源生命周期这些基本事实出发，重新构造 Java 的语言与运行模型。

## 目标：不预设 Java 的现成设计

我们要解决的问题是：怎样让开发者用相对稳定、安全的方式描述业务规则，同时让同一份程序能在不同机器上运行，并在错误发生时保留足够的信息完成恢复？

学习后应当能够：

1. 从硬件只能执行机器指令，推导源码、字节码与 JVM 的分层。
2. 区分编译期选择、运行期分派、对象身份和逻辑相等。
3. 从类型约束推导接口、泛型和反射各自承担的责任。
4. 从资源不会自动恢复这一事实，推导异常传播与确定性关闭。
5. 说明哪些是 Java 语言保证，哪些只是 OpenJDK 21 的实现。

## 拆掉现成答案

| 常见说法 | 分类 | 被隐藏的条件 |
| --- | --- | --- |
| Java 一次编译，到处运行 | 有条件结论 | 目标机器必须有兼容 class 文件版本和行为规范的 JVM，外部依赖也要可用 |
| 面向对象一定比过程式设计好 | 设计偏好 | 只有抽象边界稳定、协作关系需要替换时，多态才可能降低变化成本 |
| 接口一定优于抽象类 | 过度类比 | 是否需要共享状态、构造约束和公共实现会改变选择 |
| `equals()` 相等就一定能在 HashMap 中正确查到 | 缺条件结论 | `hashCode()` 必须满足契约，参与相等性的字段在作为键期间不能破坏定位 |
| 泛型让运行时知道 `List<String>` | 错误假设 | Java 泛型主要在编译期工作，很多类型实参会被擦除 |
| Java 传对象就是引用传递 | 错误命名 | 传入的是引用这个值的副本，而不是调用方变量本身 |
| 有 GC 就不用关闭资源 | 错误类比 | 文件描述符、连接和锁等资源有独立生命周期，GC 也没有及时性保证 |

第一性原理要求先判断这些话依赖什么，再决定它们能否作为结论。

## 从基本事实重新构造

### 从机器指令推导 JVM 分层

基本事实是：处理器最终只执行本机指令，而高级语言源码包含硬件并不认识的类型、方法和异常语义。如果每个平台都让 Java 源码直接生成机器码，语言与硬件会被紧密绑定。

Java 增加了一个稳定中间层：

```text
.java 源码
  ↓ javac：语法与类型检查
.class：字节码、常量池和结构化元数据
  ↓ JVM：校验、加载、解释或编译
当前平台的机器指令
```

![Java 源码从编译到运行的流程](/.image/interview/java/basic/java-run-flow.svg)

因此，跨平台不是魔法，而是一份分工：编译器生成满足 class 文件规范的中间表示；每个平台的 JVM 负责兑现相同语义。JVM 并不要求只能解释执行，HotSpot 可以把热点字节码即时编译为机器码。类加载、JIT 和运行时内存的详细机制统一放在 [JVM 章节](./jvm)。

### 从变化隔离推导对象、接口与多态

业务数据必须有归属，变化又不能让所有调用方同时修改。由此可以得到三种约束：

- **封装**：让状态及维护状态不变量的操作靠近，减少任意写入。
- **继承**：复用并细化一种既有类型，但会形成较强的父子耦合。
- **多态**：调用方依赖稳定契约，运行时对象决定实际行为。

```java
interface PricePolicy {
    long calculate(Order order);
}

long checkout(Order order, PricePolicy policy) {
    return policy.calculate(order);
}
```

这里真正有价值的不是“用了接口”，而是结算流程只依赖价格策略的最小契约。若业务根本不存在可替换行为，额外接口只会增加间接层。

抽象类适合表达共享状态、构造过程和公共实现；接口适合表达可以由不同类型实现的能力。两者没有脱离约束的绝对优先级。

### 从调用时机推导重载与重写

编译器必须在没有真实运行对象时检查调用是否合法，因此参数列表能够在编译期决定的选择属于 **重载**。真实对象只有运行时才确定，因此实例方法的多态选择属于 **重写与动态分派**。

```java
void print(Object value) {}
void print(String value) {}

Animal animal = new Dog();
animal.speak();
```

`print` 选择由变量的编译期类型和参数列表决定；`speak` 的具体实现由运行时对象 `Dog` 决定。只修改返回类型不能构成重载，因为调用点无法仅靠返回值消除歧义。

### 从身份与业务相等推导 `equals` 契约

内存中两个对象可以是不同实例，但业务上代表同一个用户；也可以内容暂时相同，却必须保持两个身份。因此 Java 同时保留：

- `==`：基本类型比较值，引用类型比较是否为同一引用值。
- `equals()`：由类型定义逻辑相等；`Object` 默认仍是身份相等。
- `hashCode()`：为哈希结构提供候选位置，不负责独自证明相等。

目标不变量是：只要 `a.equals(b)` 为真，`a.hashCode() == b.hashCode()` 就必须成立。反向不成立，因为有限整数空间必然允许哈希冲突。具体的桶定位和冲突处理只在 [Java 集合](./collections) 讲解。

### 从共享与可变性的代价推导不可变字符串

字符串会参与类名、路径、权限、Map 键和常量池复用。如果共享后的内容还能被任意一方修改，相等性、安全判断和缓存哈希都会失去稳定基础。

因此 `String` 对外提供不可变值语义。JDK 21 的 OpenJDK 实现使用内部 `byte[]` 与编码标记保存内容，但“内部怎样存”是版本实现；“公开 API 不能修改既有 String 值”才是稳定契约。

连续拼接需要可变缓冲区：单线程优先 `StringBuilder`；只有多个线程确实共享同一缓冲区并依赖其同步方法时才考虑 `StringBuffer`。不可变并不代表变量不能重新指向新对象。

### 从静态检查推导泛型与类型擦除

没有泛型时，容器只能暴露 `Object`，错误类型可能到运行时才失败。泛型把“容器中允许什么类型”前移到编译期：

```java
static void copy(List<? extends Number> source,
                 List<? super Number> target) {
    for (Number number : source) {
        target.add(number);
    }
}
```

`? extends Number` 表示当前引用可以安全读取 Number，但无法确定可写入哪一种具体子类型；`? super Number` 可以安全写入 Number，读取时通常只能按 Object 处理。这就是 PECS 的约束来源，而不是口诀本身。

Java 为兼容既有字节码采用擦除式泛型。编译器检查并在必要处插入转换，运行时通常只看到擦除后的原始类型。因此不能创建 `new T()`，也不能判断 `value instanceof List<String>`。

### 从参数槽复制推导 Java 的值传递

调用方法时，实参的值被复制到新的参数槽。基本类型复制数值；对象变量中保存的是引用值，所以复制的是引用值：

```java
static void update(User user) {
    user.setName("新名字");     // 两份引用都能观察同一对象
    user = new User("另一个"); // 只改当前参数槽
}
```

这同时解释了为什么方法能修改共享对象，却不能让调用方变量改指向。包装类型自动装箱后也是对象；用 `==` 比较可能受到缓存和对象身份影响，业务相等应使用 `equals()` 并在拆箱前处理 `null`。

浅拷贝只复制字段值，引用字段仍共享子对象；深拷贝还要重建需要独立的可变子图。是否复制必须从所有权和隔离需求推导，不应默认用序列化完成。

### 从失败传播推导异常和资源关闭

调用可能正常返回，也可能无法履行契约。Java 用 `Throwable` 表示异常完成：`Error` 通常表示应用难以局部恢复的运行环境问题；`Exception` 表示程序可以建模或处理的失败，其中受检异常要求调用链显式声明或捕获。

异常不等于恢复。捕获后必须做出明确动作：补充上下文并继续抛出、转换成业务错误、执行补偿，或在真正可恢复时返回降级结果。空 `catch` 会破坏可观察性。

资源释放必须在成功和异常路径都成立。`try-with-resources` 根据 `AutoCloseable` 契约生成确定性关闭路径，按声明的逆序关闭资源，并通过 suppressed exception 保留关闭阶段的次要异常。

`final` 是语言约束，`finally` 是异常控制流，`finalize()` 则是已弃用且不可靠的回收回调。三者名称相似但不存在共同机制。

### 从运行时扩展推导注解与反射

编译期类型系统无法预知所有运行时配置，框架又需要发现类型、构造对象和连接元数据。因此 Java 提供：

- **注解**：结构化元数据，本身不会自动执行业务逻辑。
- **反射**：运行时检查类、字段、方法和构造器，并执行动态调用。

只有编译器、注解处理器或运行时框架读取注解后，它才产生效果。反射换取通用性，同时削弱静态可见性、封装边界和重构安全；能用接口或显式注册完成时，不应默认使用反射。

## 固定版本的实现与源码验证

本章的稳定语义以 Java SE 21 为准，OpenJDK 只用于证明一个固定版本怎样实现这些语义：

- [Java Language Specification, Java SE 21](https://docs.oracle.com/javase/specs/jls/se21/html/index.html)：类型、类、表达式、异常和泛型的语言保证。
- [Java Virtual Machine Specification, Java SE 21](https://docs.oracle.com/javase/specs/jvms/se21/html/index.html)：class 文件、指令集与 JVM 公共契约。
- [OpenJDK `jdk-21-ga`](https://github.com/openjdk/jdk/tree/jdk-21-ga)：固定源码入口。
- [`String.java`](https://github.com/openjdk/jdk/blob/jdk-21-ga/src/java.base/share/classes/java/lang/String.java)：JDK 21 的字符串存储与操作实现。
- [`ClassLoader.java`](https://github.com/openjdk/jdk/blob/jdk-21-ga/src/java.base/share/classes/java/lang/ClassLoader.java)：类加载 API 的实现入口，加载细节在 JVM 章节展开。

规范没有要求 JVM 必须使用 HotSpot 的对象头、解释器或 JIT 策略；这些实现不能反过来定义 Java 语言。

## 最小实验：观察字节码与对象语义

### 实验一：源码不是处理器的直接输入

```bash
javac DispatchDemo.java
javap -c -v DispatchDemo
```

观察 class 文件版本、常量池和 `invokevirtual` 等指令，再改变运行时对象，验证同一个调用点可以分派到不同实现。

### 实验二：相等与哈希必须同时稳定

```java
record UserId(long value) {}

var left = new UserId(7);
var right = new UserId(7);
System.out.println(left == right);      // false
System.out.println(left.equals(right)); // true
```

把一个可变对象作为 HashMap 键，再修改参与 `equals/hashCode` 的字段；如果查找失败，证伪的是“只要对象还在 Map 中就一定能找到”。

### 实验三：主要异常不会被关闭异常覆盖

创建一个 `close()` 也抛异常的 `AutoCloseable`，在 try 块中先抛出主异常，检查 `getSuppressed()`。这可以验证 try-with-resources 的恢复信息模型。

## 验证与证伪

| 要验证的结论 | 改变条件 | 预期观察 |
| --- | --- | --- |
| 字节码是跨平台契约 | 用低版本 JVM 运行高版本 class | 兼容性条件不满足，跨平台结论失效 |
| 重载在编译期选择 | 改变变量声明类型但保持运行对象不变 | 可能选择不同重载 |
| 重写在运行期分派 | 保持声明类型不变，替换实际子类 | 调用不同实现 |
| Java 是值传递 | 在方法内让参数重新指向新对象 | 调用方变量不改变 |
| 注解不会自己执行 | 只定义注解，不提供处理器 | 不产生业务效果 |
| GC 不等于资源关闭 | 忘记关闭连接并等待 GC | 释放时间不可作为正确性保证 |

## 工程取舍与失败边界

- 静态类型减少一部分运行时错误，但不能证明业务数据有效或外部系统成功。
- 继承能复用实现，也会放大父类变化；组合和接口同样有间接层成本。
- 不可变对象更易共享，但频繁创建大对象会增加分配和回收压力。
- 泛型增强编译期安全，却无法保留全部运行时类型信息。
- 反射与注解适合框架边界，不适合掩盖业务依赖。
- 异常只能传播失败信息；事务、幂等与补偿属于更高层恢复机制。
