# 第一性原理内容编写规范

本规范用于新增、改写和审核“葵花宝典”与“天机秘卷”的技术内容。本站采用马斯克常用的第一性原理表述：把问题拆到尽可能确定的基本事实，从这些事实向上推理，而不是因为行业惯例、既有产品或相似案例就接受答案。面试问题是理解检查，不是正文的组织单位。

## 1. 内容归属：一份正文，两个入口

每个概念只保留一个主归属。第一性原理学习地图按基本问题组织学习顺序，技术索引按语言、框架和组件提供查阅入口；两者只链接同一正文，不复制答案。

| 主归属 | 核心问题 | 不收录的内容 |
| --- | --- | --- |
| `java/` | 语言、数据结构、并发和运行时怎样保证单机程序正确 | Spring、数据库和分布式中间件 |
| `web/` | 字节、缓冲、连接、协议和事件循环怎样传递信息 | Spring MVC 注解和业务配置 |
| `spring/`、`persistence/` | 应用怎样组织对象、请求、事务和 SQL 映射 | 存储引擎和分布式一致性理论 |
| `mysql/`、`redis/` | 状态怎样索引、并发访问、持久化和缓存 | 消息投递与消费语义 |
| `middleware/`、`integration/` | 异步事件、任务和异构系统怎样可靠协作 | CAP 等通用分布式理论 |
| `distributed/`、`microservices/` | 多节点怎样处理部分失败、一致性和服务治理 | 单机框架基础用法 |
| `engineering/`、`operations/` | 系统怎样控制变化、验证、发布、观测和恢复 | 具体业务协议 |
| `ai/` | 概率模型怎样在确定性规则和权限边界内工作 | 把通用后端机制重新讲一遍 |
| `iot/`、`frontend/` | 通用原理怎样在特定领域和协作边界中落地 | 可迁移原理的重复答案 |

目录层级保持“知识域 / 主题页”。只有当一个页面无法形成连续推导、内容过长影响阅读，或实现版本存在清晰边界时才拆页。现有 URL 优先保留，避免破坏外链。

## 2. 第一性原理的四步写法

### 第一步：定义目标，不预设方案

先写清真正想得到的结果和必须保持的不变量，标题中暂时不要出现具体实现。例如不要从“为什么用 HashMap”开始，而要先问“怎样按 Key 定位对象，并让同一 Key 只对应一个值”。

### 第二步：拆掉现成答案

把已有认知逐条分类：

| 类型 | 判定方式 | 能否作为推理起点 |
| --- | --- | --- |
| 基本事实 | 可由规范、源码、实验或稳定现象验证 | 可以 |
| 硬约束 | 资源、网络、权限、业务规则不可绕过 | 可以 |
| 目标不变量 | 系统无论怎样执行都必须保持的结果 | 可以 |
| 假设 | 当前条件下可能成立，但需要验证 | 不能直接使用 |
| 惯例或类比 | “过去这样做”“别的系统这样做” | 只能作为候选方案 |

例如“网络会超时”是可观察事实，“超时说明服务端没执行”是假设，“接 MQ 就不会丢消息”是行业口号。文章必须主动暴露这些差异。

### 第三步：从基本事实重新构造

暂时忘掉框架和产品名，只使用基本事实、硬约束和目标不变量，构造最小的数据、状态与控制关系。每增加一个组件或步骤，都要回答：它保护哪个不变量？如果去掉它，哪条故障路径会重新出现？

### 第四步：验证并尝试证伪

再用固定版本源码、最小实验、日志或真实案例验证推导。除了成功路径，还要改变数据规模、并发条件、故障位置和权限边界，寻找能推翻结论的反例。验证失败时修改假设或方案，不能为了保留原答案挑选证据。

第一性原理不等于每篇文章都从数学、晶体管或物理定律讲起。拆解应停在“已经可验证，且足以重新构造当前机制”的最低必要层级。

## 3. 主题页标准结构

```md
---
outline: [2, 3]
---

# 主题名称：它解决什么基本问题

## 目标：不预设技术方案
真正要得到的结果、目标不变量和适用边界。

## 拆掉现成答案
列出常见说法，并区分基本事实、硬约束、假设、惯例和类比。

## 从基本事实重新构造
去掉框架名，只根据事实和不变量逐步推出最小机制。

## 实现与源码验证
固定版本、源码入口、2～4 个关键分支，以及实现与稳定原理的对应关系。

## 验证与证伪
用源码、实验或故障注入验证，并说明什么证据会推翻结论。

## 工程取舍与失败边界
适用条件、成本、反例、排障和恢复。

## 理解自测与面试表达
反事实问题、场景选择、排障题，以及 30 秒和 3 分钟表达骨架。

## 参考资料
官方文档、规范、源码、论文或可复现实验。
```

结构允许按主题合并或细分，但“目标、假设拆解、基本事实、重新构造、验证证伪、自测”不可缺失。源码、代码和流程图只在能验证核心机制时加入，不作为篇幅装饰。

## 4. 推导、源码与证据

### 先讲稳定原理，再讲版本实现

- JDK、Spring、MySQL、Redis、RocketMQ 等实现会演进；源码必须注明版本、类/方法/模块和 2～4 个有意义的分支。
- 不逐行翻译源码。先说明要验证的机制，再展示实现怎样满足它。
- 不把某个版本的阈值、默认值或内部数据结构写成永恒规律。
- 不能从“源码就是这样写的”反推这是唯一合理方案；先独立推导，再解释实现选择。

### 让结论可以被验证

- 能用最小代码或实验验证时，给出输入、观察点和预期结果。
- 性能、容量、QPS、延迟和成本数字必须带环境、时间范围与测量口径；没有证据时使用定性描述。
- 项目案例明确标注“生产已验证”“本地/技术验证”或“通用方案”。不能把建议方案包装成个人经历。
- 事实来源优先级为：官方规范和源码 → 可复现实验 → 权威书籍或论文 → 公开案例。

## 5. 图示与示例

- 状态迁移、并发共享、网络 I/O、消息投递、事务和故障恢复等复杂机制，优先使用一张只表达一个核心关系的图。
- 优先复用现有 SVG；新图必须遵循 [`docs/diagrams.md`](../../docs/diagrams.md)，保留内嵌 draw.io 数据、明暗主题和准确中文替代文本。
- 示例代码保持最小可读，展示关键前提、状态和错误处理；不要粘贴与结论无关的完整业务代码。
- 白话类比只能在完成第一性推导后帮助建立直觉，不能作为结论的证据，更不能用“它像某物”替代机制。

## 6. 理解自测与面试表达

面试问题集中放在章节末尾，承担四种检查：

- **因果题：** 为什么需要这个机制？去掉其中一步会怎样？
- **反事实题：** 如果数据规模、并发模型或故障条件改变，结论是否仍成立？
- **选择题：** 给定场景和约束，怎样选择方案并说明代价？
- **排障题：** 出现超时、重复、积压、错误状态或性能下降时，先观察什么？

每章提供两种表达骨架：30 秒先说问题、核心机制和一个边界；3 分钟补充推导、实现证据、工程取舍与失败恢复。不要为每个知识点重复写一段无法推导的“面试一句话”。

迁移旧页面时，原有问题必须映射到正文或自测区，不能静默删除。需要兼容旧深链接时，保留原问题标题作为自测小节，并用链接指回主原理段落，避免复制完整答案。

## 7. 审核准入标准

提交前逐项确认：

1. 文章先定义结果，没有把现成产品或框架当作问题本身。
2. 常见答案中的事实、假设、惯例和类比已经显式区分。
3. 机制只从可验证的基本事实、硬约束和目标不变量重新构造。
4. 稳定原理与版本实现已经分开，源码和图示与正文一致。
5. 至少给出一个验证方法和一个可能推翻结论的反例条件。
6. 代价、错误表现和恢复方式没有被省略。
7. 项目证据、性能数字和高风险操作均写清边界。
8. 内容没有和其他页面重复；旧问题已经完成映射。
9. 已执行 `pnpm diagrams:check`、`pnpm docs:build` 和 `git diff --check`。
