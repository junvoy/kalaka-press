# 面试题内容编写规范

本规范用于新增、改写和审核“葵花宝典”面试题。目标是让读者既能在面试中准确作答，也能知道答案在什么条件下才成立；不把百科摘抄、源码细枝末节或未经验证的项目说法伪装成结论。

## 1. 目录归属规范

先按“题目的第一知识归属”放置，再判断是否需要交叉链接。不要因为一个技术同时被多个系统使用，就在多个目录各写一份答案。

| 归属 | 收录范围 | 不收录的内容 |
| --- | --- | --- |
| `java/` | 语言语法、标准库、并发、线程管理、JVM、JDK 新特性 | Spring、数据库、MQ、分布式中间件 |
| `web/` | 网络协议、HTTP、I/O、NIO、连接和文件 | Spring MVC 的框架机制 |
| `spring/` | IoC、AOP、Spring Boot、Spring MVC、事务 | MySQL 索引、Redis 数据结构 |
| `persistence/` | ORM、SQL 映射、对象与结果集转换 | 数据库内核与缓存策略 |
| `mysql/`、`redis/` | 数据存储、事务、索引、缓存、数据一致性 | 消息投递与消费语义 |
| `middleware/`、`integration/` | 消息、调度、文件/接口集成、批处理 | CAP、分布式事务的通用理论 |
| `distributed/`、`microservices/` | 跨节点一致性、容错、服务治理、RPC、网关 | 单机框架的基础用法 |
| `engineering/`、`operations/` | 测试、代码质量、发布、监控、排障 | 具体业务协议 |
| `iot/`、`frontend/` | 特定业务领域和协作边界 | 可迁移的通用原理 |

目录层级固定为“知识域 / 主题页”。一个主题页放一组连续追问，例如 Spring 的 IoC、Bean、AOP 与事务；只有内容量、读者入口或版本差异足够大时才拆成多页。新主题页使用描述性目录名和 `question.md`，例如 `src/interview/security/question.md`。

## 2. 页面最小结构

每个主题页必须具备以下结构，便于侧边栏、站内搜索和读者快速复习：

```md
---
outline: [2, 3]
---

# 主题名称面试题

本章解决什么问题、适合哪些岗位；说明与相邻章节的边界。

## 子主题

### 1. 面试官会怎样问？

**面试一句话：** 20～80 字，先给可直接口述的准确结论。

**展开说明：** 说明机制、因果关系和必要术语。

**源码解析（核心机制必填）：** 标明实现或框架版本、源码入口（类 / 方法 / 模块）和 2～4 个关键分支；用伪代码或经过裁剪的原始代码解释“它为什么这样做”。源码解析服务于理解，不逐行翻译，也不把版本相关细节说成固定规律。

**例子或场景：** 用小代码、请求链路或业务场景证明答案能落地。

**边界与误区：** 写清前提、版本差异、反例或常见错误。

**可追问：** 列出 1～3 个自然的下一问；复杂主题可链接到本章后续题。
```

短题也至少要有“面试一句话”和“边界与误区”。涉及容器、代理、线程调度、网络 I/O、消息投递、缓存一致性、事务或状态迁移等核心机制时，必须加入“源码解析”；只有在确实能帮助理解时才加入代码、表格或流程图。图示必须有准确中文替代文本，流程图遵循仓库的 `docs/diagrams.md` 约定。

## 3. 单题写作要求

### 问题要可回答、可追问

- 题干使用一个明确问题，避免“聊聊 X”“深入理解 X”这类无法判断范围的标题。
- 同一子主题按“概念 → 原理 → 选型/实践 → 排障/边界”排序；编号在主题页内连续。
- 把可以相互追问的概念放在相邻位置。例如“消息是否重复”之后接“幂等消费”和“重试/死信”。
- 一个答案只解释一个核心结论。需要比较时，用表格列出维度和适用条件，不堆砌名词。

### 结论必须带条件

- 不写绝对化表述，如“Redis 一定更快”“POST 一定不幂等”“`volatile` 能保证线程安全”。改为说明依赖的操作、数据规模、部署方式和版本。
- JDK、Spring、MySQL、Redis 等实现会演进。源码行为、默认参数和版本特性必须注明版本；稳定原理与版本细节分开描述。
- 性能、容量、QPS、延迟、成本等数字必须写明测量口径、环境和时间范围；没有证据时用定性描述，不编造数字。
- 项目例子需要区分“生产已验证”“本地/技术验证”“建议方案”。不得把学习、推测或他人案例写成真实线上经历。

### 技术表达要面向面试

- 先用中文解释，再首次给出必要英文术语和代码标识；避免只翻译名词不解释机制。
- 一句话回答能在 30 秒内自然说出；展开说明用于 1～3 分钟追问。不要将背诵稿写成大段口号。
- 示例代码应最小可读，展示关键前提和错误处理；不贴与结论无关的配置或完整业务代码。
- 源码解析要先给稳定结论，再给实现入口和关键分支；JDK、Spring、MySQL、Redis 等必须标明版本或实现范围，并附官方源码 / 文档链接。
- 安全、资金、数据删除、权限等高风险场景必须写清校验、幂等、审计、回滚或人工介入边界。

## 4. 事实与来源要求

优先级依次为：官方文档/规范和源码 → 可复现实验 → 权威书籍或论文 → 公开案例。引用外部资料时，在题末以“参考资料”列出链接或书名；不要大段复制第三方内容。

提交前逐项确认：

1. 结论与当前稳定版本或引用来源一致，版本差异已标注。
2. 题目没有和其他页面重复；若存在交集，已链接到唯一主答案。
3. “面试一句话”可独立成立，正文没有与其矛盾。
4. 代码、SQL、配置和流程图与文字说明一致，并已隐藏凭证、真实客户数据和内部地址。
5. 新增图示已按仓库流程图约定检查；所有改动已执行 `pnpm docs:build`。

## 5. 审核准入标准

一题达到以下标准才进入主干内容：准确、有边界、能口述、可验证、与目录不重复。内容仍在探索或依赖特定项目时，可保留，但要显式标为“技术验证”或“项目特定”，不能混入通用高频结论。

如果题目来自一次真实面试复盘，先把原始问题和适用岗位记录在复盘材料中，再提炼为不含公司、个人和敏感业务信息的通用题目。这样既保留真实上下文，也不会让宝典变成零散面经。
