# Redis 面试题

Redis 常用于缓存、计数、排行榜、会话和部分协调场景。它快不等于可以把它当成数据库替身：设计时要同时说明数据结构、过期、持久化、容量和一致性边界。

## 基础与性能

### 1. Redis 的数据模型和常用结构是什么？

**面试一句话：** Redis 以二进制安全的 key-value 为基础，提供 String、Hash、List、Set、ZSet、Stream 等结构；应按访问模式选择结构，而不是把所有对象都序列化成一个大 JSON。

String 适合计数和短值，Hash 适合字段级读取，ZSet 适合按分数排序，Stream 适合可确认的消费流。一个 key 的 TTL 是作用于整个 key，不是 Hash 内某个字段；大 key 会拖慢网络、删除和复制，应提前限制大小。

### 2. Redis 为什么通常很快？

**面试一句话：** Redis 的常见命令主要在内存中完成，单个事件循环通过 I/O 多路复用处理大量连接，命令执行路径通常短；但慢命令、大 key、持久化和网络仍会造成延迟。

![Redis 命令从 I/O 多路复用事件到执行和返回结果的关键流程](/.image/interview/redis/event-loop/redis-command-flow.svg)

不要把“单线程”说成所有工作都只有一个线程：Redis 版本和配置下，网络 I/O、持久化或后台清理可以有辅助线程；稳定结论是核心命令执行应避免长时间阻塞事件循环。

#### 源码解析：事件循环只在就绪后执行命令

以 Redis 7 的 [`ae.c`](https://github.com/redis/redis/blob/7.4/src/ae.c) 和 [`networking.c`](https://github.com/redis/redis/blob/7.4/src/networking.c) 为入口，`aeMain` 循环调用 `aeProcessEvents`，由 epoll/kqueue/select 报告就绪 socket；读事件回调读取请求并解析 RESP，再进入命令执行。I/O 多路复用不是“一个线程同时执行多个命令”，而是一个线程等待多个连接的就绪通知，随后快速处理当前就绪事件。

### 3. Redis 可以用来做什么？哪些情况不适合？

**面试一句话：** Redis 适合热点缓存、短期验证码、限流计数、排行榜、会话和延迟敏感的临时状态；不适合替代需要复杂查询、强事务约束和长期权威审计的关系数据库。

缓存数据必须能从权威数据恢复。资金余额、扣减和不可丢失订单等场景，即使使用 Redis 做加速或协调，也应明确数据库事务、幂等和补偿的最终边界。

## 缓存一致性与高可用

### 4. 缓存与数据库怎样保证最终一致？

**面试一句话：** 常见读路径是 Cache Aside：先读缓存，未命中再读数据库并回填；写路径先更新数据库，再删除缓存，让后续读回填新值。它追求最终一致，不是强一致事务。

删除缓存失败要通过重试、消息或订阅 Binlog 等可靠机制补偿；不要简单地“先删缓存再更新数据库”，否则并发读可能把旧值重新写回缓存。高一致需求应优先读权威库或设计版本校验。

### 5. 缓存穿透、击穿和雪崩怎样区分？

| 问题 | 触发条件 | 常见处理 | 边界 |
| --- | --- | --- | --- |
| 穿透 | 高频查询根本不存在的数据 | 空值缓存、布隆过滤器、参数校验 | 布隆过滤器可误判，空值要有短 TTL |
| 击穿 | 热点 key 失效后并发回源 | 单飞 / 互斥重建、逻辑过期 | 不要让等待线程无限堆积 |
| 雪崩 | 大批 key 同时失效或 Redis 故障 | TTL 打散、高可用、限流降级 | 数据库必须有兜底容量 |

**面试一句话：** 三者的共同结果都是回源压力，但根因分别是不存在的数据、单个热点失效和大量 key 或缓存服务同时不可用，所以治理手段不同。

### 6. Redis + 本地缓存的二级缓存怎么设计？

**面试一句话：** 本地缓存减少进程内热点读取延迟，Redis 负责跨实例共享；两级缓存要使用版本、失效通知或较短本地 TTL 控制数据陈旧，并在缓存未命中时通过单飞或互斥避免回源风暴。

本地缓存不是所有数据都适合放。多实例数据一致性要求高、更新频繁或租户隔离严格的数据，应优先评估是否只用 Redis 或直接查询权威数据；缓存 Key 必须包含租户、环境等隔离维度。

## 锁、过期与持久化

### 7. 分布式锁的最小正确实现是什么？

**面试一句话：** 获取锁应使用带唯一 token 和过期时间的一条原子命令，例如 `SET lock token NX PX 30000`；释放时必须比较 token 后再删除，通常用 Lua 保证“比较 + 删除”原子。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

过期时间只能降低死锁风险，不能证明临界区一定安全：业务执行超过租约后，旧持有者可能继续写入。涉及外部副作用时还要结合幂等、版本号或 fencing token；不要用 Redis 锁替代数据库唯一约束和业务状态机。

### 8. Redisson 的可重入锁与看门狗怎样理解？

**面试一句话：** Redisson 的可重入锁用“客户端标识 + 线程标识”记录持有者并维护重入计数；未显式指定租约时，看门狗会在持有期间续期，降低业务未完成就过期的概率。

看门狗不是无限可靠：进程长时间暂停、网络隔离或 Redis 故障仍可能造成租约丢失。显式租约、业务耗时、重试策略和幂等设计要一起评估；锁竞争严重时要先检查能否按业务 key 拆分或改成队列。

### 9. RDB 和 AOF 有什么区别？

**面试一句话：** RDB 以某一时刻的数据快照恢复快、文件紧凑；AOF 记录写命令，通常能缩小丢失窗口但文件更大且需要重写。实际可靠性取决于刷盘策略、复制和故障切换方案。

`appendfsync everysec` 常被用作性能与数据丢失窗口的折中，但它不承诺零丢失。面试中应说明“能丢多少数据、如何恢复、主从切换时如何处理”，而不是只罗列持久化名称。

### 10. Redis 慢或内存持续增长时怎样排查？

**面试一句话：** 先确认延迟发生在客户端、网络还是服务端，再检查慢日志、命令耗时、大 key、热 key、内存碎片、过期淘汰、持久化和复制延迟，最后用压测或灰度验证修复。

不要直接执行可能阻塞的全量 `KEYS *` 排查生产问题；优先用 `SCAN`、`SLOWLOG`、`INFO`、采样和受限时段操作。淘汰策略也必须与业务容忍度匹配，不能让关键状态被当作普通缓存驱逐。
